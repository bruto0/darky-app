## 1. Задача и рамки

Нужно мобильное приложение клиента студии, повторяющее личный кабинет виджета impulseCRM:

- вход по телефону и паролю **нативно** (D15): `phone_info` → `check_password` → `search`;
- восстановление пароля — ссылка открывает `/widget/2` во внешнем браузере (D16);
- после входа приложение получает `client_id` и `secret` и работает с клиентским API виджета;
- разделы: абонемент, расписание, посещения, покупки, записи;
- профиль, бонусы, QR/штрихкод, выход.

Что **сохраняем** из веба: состав данных, названия разделов, логику абонемента, расписание по дням, фильтры по залу и преподавателю, карточки занятий, стикеры, замены, отмену записи.

Что **меняем**:

1. **Навигация.** Верхние табы веба обрезают подписи («Абоне…», «Посещ…»). В приложении — нижняя навигация на 4 раздела. Это мобильная норма и снимает обрезку.
2. **Расписание без вложенного скролла.** В вебе расписание — iframe высотой 800 px со своим скроллом. В приложении весь экран «Абонемент» — один скролл; список занятий выкладывается на всю длину. Требование №1 задачи.
3. **Фон расписания следует выбранной теме (D11).** Светлая — фон страницы, тёмная — тёмный фон. В вебе блок всегда розовый.
4. **Индивидуальные занятия.** В веб-виджете они выключены (`individualEnable: false`). В приложении включаем `individuals: true` и показываем по правилу приватности (§5.3). Требование №2.
5. **Приватность аренды.** В вебе карточка аренды показывает ФИО клиента. В приложении чужую аренду показываем как «аренда» + зал, свою — с именем (D4 — принято).
6. **Один скролл на раздел.** Посещения и покупки листаются бесконечно (подгрузка страниц), без внутренних «окон» с прокруткой.
7. **Две темы и меню.** Выбор темы — в отдельном диалоге, доступном из меню «три точки» справа от выхода (D1). Темы: Светлая и Тёмная.
8. **FAB обновления расписания.** Круглая кнопка в правом нижнем углу, перетаскивается по экрану, но всегда целиком остаётся в safe area; тап — обновить день.
9. **Без оплаты.** Кнопка «Оплатить» убрана; «Заморозить» — full width в карточке абонемента, где заморозка доступна; у «Стандарт» — пояснение (D5).

Вне рамок MVP: онлайн-оплата (убрана из приложения), запись на групповые занятия, push-уведомления, офлайн-режим. BFF **не планируется** (D10). Нативная заморозка — этап 8; в MVP кнопка открывает веб-сценарий клуба.

### 1.1. Какой API использует приложение

В папке [docs/](../docs/) два контура:

| Контур | Авторизация | Годится для клиентского приложения? |
|---|---|---|
| Документированный `/api/public/<сущность>/*` | `Authorization: Basic <API_KEY>` | **Нет.** `client_id`/`secret` к нему не подходят (401). Это API ключа клуба/интеграций, его нельзя класть в APK. |
| Клиентский виджет `widget_*` | `client_id` + `secret` (кроме публичного расписания) | **Да.** Именно его использует веб-кабинет `/widget/2`. |

Поэтому «использовать полученные `client_id` и `secret` для запросов к API» в этой задаче означает клиентские методы виджета: `widget_client_lk/accounts`, `visits`, `deposits`, `schedule`, `barcode`, `search`, `widget_schedule/list`, `widget_schedule/stickers`, `widget_schedule/changes`. Документированный API из `docs/impulsecrm-api/` остаётся справочником по полям для сотрудничьего контура; BFF не планируется.

Общее расписание (`widget_schedule/list`) вендор отдаёт **без авторизации**, как и веб-виджет. Приложение запрашивает его так же; `client_id`/`secret` нужны для персональных данных (абонементы, посещения, покупки, «мои записи»).

## 2. Визуальный язык

### 2.1. Идея

«Тихая роскошь» танцевальной студии: тёплый светлый фон, розовый бренд-акцент из виджета клуба, глубокий графитовый текст. Чёрная иконка с сине-фиолетовой `D` — самостоятельный знак; в интерфейсе фиолетовый появляется только там, где важно отличить **своё** занятие и защищённые действия. Никакого «неона» и градиентного шума: карточки, воздух, крупные цифры. Базовая тема — светлая; доступна также тёмная (2.3).

### 2.2. Палитра

| Токен | HEX | Где используется |
|---|---|---|
| `bg` | `#F8F5F8` | фон экранов, тёплый светло-лиловый |
| `surface` | `#FFFFFF` | карточки, поля, нижняя навигация |
| `ink` | `#18141D` | основной текст, активный день, primary-кнопка |
| `ink-2` | `#3F3949` | вторичный текст, имена преподавателей |
| `muted` | `#8D8697` | подписи, время, залы |
| `line` | `#ECE7EF` | разделители, обводки |
| `pink` | `#C27BA0` | бренд-акцент: активный таб, заливка абонемента |
| `pink-deep` | `#9E5B7E` | активные подписи, суммы, чипы |
| `pink-soft` | `#F6E7EF` | мягкие плашки, бонусы, дата записи |
| `violet` | `#6C5CE7` | «моё» занятие, безопасность, QR |

Градиент иконки: `#6A8BFF → #8B5CF6 → #B06CF0` на `#000000`.

### 2.3. Две темы

Выбор — в диалоге из меню «три точки» (справа от выхода). Тема применяется сразу и сохраняется между запусками.

| Тема | Фон / карточки | Акцент | Расписание (D11) |
|---|---|---|---|
| **Светлая** (по умолчанию) | `#F8F5F8` / `#FFFFFF` | розовый `#C27BA0` | фон страницы, белые карточки |
| **Тёмная «Графит»** | `#0D0C11` / `#17151D` | розовый `#E39BC2`, фиолетовый `#A99BFF` | тёмный фон страницы |

Общие правила:

- текст и иконки не теряют контраст: в тёмной теме `ink` — светлый, `surface` — графит; в светлой — тёмный текст на белом;
- абонемент в каждой теме имеет свой градиент, но остаётся самым «плотным» акцентом экрана;
- активный день недели: в светлой — `ink` с белым текстом, в тёмной — светлая плашка с тёмным текстом;
- ошибки/отмены остаются красными, оплаты — зелёными; смысл не передаётся только цветом;
- фон расписания — часть темы (D11), а не отдельная настройка.

### 2.4. Типографика

**Manrope** (кириллица, 400/500/600/700/800), запасной — системный `Roboto`/`Segoe UI`.

| Роль | Размер / высота | Вес | Пример |
|---|---|---|---|
| H1 экрана | 27/32 | 800, −4% | «Посещения» |
| H2 секции | 20/24 | 800, −3% | «Расписание» |

### 2.5. Сетка, радиусы, тени

- Поля экрана: 20 px; между карточками: 7–9 px; секции: 18–20 px.
- Радиусы: карточки 16–17, абонемент 22, кнопки 14, фильтры 13, нижняя навигация 0.
- Тени мягкие, только для приподнятых поверхностей: `0 4px 14px rgba(30,20,40,.045)`.
- Иконки: stroke 1.8, 20–22 px; активные — заливка/акцент.
- Минимальная зона нажатия: 44×44 (лучше 48×48).

## 3. Информационная архитектура

```
BottomNav
├─ Абонемент (home)
│   ├─ профиль: аватар, имя, бонусы, QR, выход, меню ⋮
│   ├─ абонемент(ы): остатки, срок, заморозка per-account
│   └─ расписание: фильтры, неделя, день, список занятий + FAB обновления
├─ Посещения: история визитов, пагинация
├─ Покупки: оплаты и пополнения по месяцам
└─ Записи: свои занятия/аренды, отмена
```

Меню ⋮ → «Тема оформления» (диалог двух тем) и «О приложении».
Почему расписание внутри «Абонемента», а не отдельным табом: так в вебе, и так клиент видит свои остатки и сетку в одном контексте. Требование «расписание в полный размер» решается одним скроллом, а не отдельным табом.

## 4. Экраны

### 4.1. Вход (нативный, вариант A, D15)

**Цель:** быстрый и предсказуемый вход без тяжёлого WebView; телефон и пароль
вводятся в нативных полях, пароль уходит в API клуба по HTTPS и не сохраняется.

**Композиция:**

- фон выбранной темы (`AppPalette.bg`), без «тёмной бренд-карточки»;
- шапка: иконка-плитка `D`, слово `D'arky`, подпись «D'arky Dance · личный кабинет»;
- заголовок «Вход в личный кабинет», пояснение «Введите телефон и пароль…»;
- карточка `surface` с рамкой `line`: поле телефона (маска, `inputmode=tel`),
  поле пароля с eye-toggle, primary-кнопка «Войти»;
- под карточкой ссылка **«Восстановить пароль»** и пояснение, что откроется
  страница клуба в браузере;
- нижняя подпись с замком: «Пароль передаётся клубу по HTTPS и не сохраняется
  в приложении», домен тенанта.

**Состояния:**

1. Пусто: кнопка «Войти» активна, ошибок нет.
2. Валидация: пустые поля — «Введите телефон и пароль», фокус на первом пустом.
3. Загрузка: спиннер в кнопке, поля disabled, повторный тап игнорируется.
4. Ошибка API: плашка в карточке; пароль очищается, фокус в поле пароля.
   Тексты: «Телефон не найден в клубе», «Неверный пароль», «Для этого номера
   не задан пароль. Воспользуйтесь восстановлением», сетевые ошибки.
5. Успех: `TextInput.finishAutofillContext(shouldSave: true)` (Android может
   предложить сохранить пароль), сессия в Keystore, переход на «Абонемент».

**Автозаполнение:** нативные `TextField` в `AutofillGroup`:
`AutofillHints.username` + `telephoneNumber` для телефона,
`AutofillHints.password` для пароля. Это стандартный Android Autofill,
без WebView-эвристик и без сторонних полей.

**Восстановление пароля:** отдельного URL у вендора нет — восстановление
открывается модалкой внутри `/widget/2` (Telegram / MAX / входящий звонок).
Кнопка открывает `https://<tenant>/widget/2` во **внешнем браузере**
(`url_launcher`, `LaunchMode.externalApplication`), пользователь нажимает
«восстановить пароль» и выбирает способ. Приложение не вмешивается в поток.

**Безопасность:** пароль проходит через память приложения (выбор D15), но не
пишется в логи, secure storage, analytics и не попадает в скриншоты release
(`FLAG_SECURE`); очищается после запроса. TLS — стандартный для Dio/OkHttp (L2).
Это осознанный компромисс: D15 выбран ради скорости и стабильного autofill;
BFF по-прежнему не планируется (D10). Подробности и ограничения WebView —
в [WEBVIEW-NOTES.md](WEBVIEW-NOTES.md).

### 4.2. Абонемент (главная)

**Структура сверху вниз:**

1. Профиль: аватар (фото из `fotoThumbUrl`, иначе инициалы), имя, бонусный чип `★ 0` во второй строке, кнопка выхода и меню `⋮` **справа от выхода**. QR-кнопка с главной убрана по запросу.
2. Список абонементов: отдельная карточка на каждый активный абонемент, со своими счётчиками и сроком. Цвет карточки — из типа/`typeColor` (в вебе «Профи» розовый, «Стандарт» зелёный), с адаптацией под тему.
3. Заморозка: **per-account**. Кнопка «Заморозить» на всю ширину — только внутри карточки, где заморозка реально доступна. Если тариф без заморозки — кнопки нет, есть пояснение «Заморозка не предусмотрена тарифом». Кнопки «Оплатить» нет (D5).
4. Заголовок «Расписание» + «Сегодня, 19 ноября».
5. Фильтры «Зал · Все» и «Преподаватель · Все».
6. Неделя: Пн–Вс, активный день.
7. Список занятий на день — **полной высоты, без своего скролла**.
8. FAB обновления расписания — круг 52 в правом нижнем углу (см. §4.3).

**Счётчики абонемента:** 5 значений в сетке 2×2 + одна широкая строка, если пакеты есть:

- занятия: `trainingsLeft / trainingsTotal`;
- заморозка: дни (из пакета заморозки/полей `freeze*`);
- самоподготовка, персональная диагностика, гостевые визиты: `count - used / count` с названием из `packets[].type`.

Если пакетов нет (как у «Стандарт») — карточка компактная: только занятия и срок.

#### Заморозка по абонементам (проверено 19.11.2026)

У текущего клиента **два активных абонемента**:

| Абонемент | Остаток | Заморозка | Карточка |
|---|---|---|---|
| «Профи» (`groupAccount`) | 20 / 24 занятий | **21 / 21 день**, пакет `{days:21, min:"1"}`; кнопка открывает период «от 1 дня» | розовая, кнопка full width |
| «Стандарт» (`individualAccount`) | 3 / 5 занятий | **нет**: `packets: []`, нет дней заморозки, в вебе нет действия | зелёная, пояснение без кнопки |

В вебе кнопка «Заморозить» одна на весь кабинет и стоит после карточек; из неё неочевидно, к какому абонементу она относится. В приложении делаем **кнопку в каждой карточке, где заморозка доступна** — это исключает заморозку «не того» абонемента и честно показывает тариф «Стандарт».

**Правило доступности:** `freezeEnable` из конфига виджета **и** активный, не закрытый, не уже замороженный абонемент **и** остаток дней заморозки > 0 (пакет с `days` или `freezeDays`). Если условие не выполнено — действия нет, показываем причину.

**Несколько абонементов:** вертикальный список карточек; закрытые — свёрнуты в «Архив» (в вебе `closedAccountsShown:false`; у клиента закрытых нет).

В MVP кнопка заморозки открывает веб-сценарий клуба в модальном WebView: у клиента только один абонемент с заморозкой, поэтому выбор однозначен. Если позже заморозка появится у нескольких абонементов, нужен нативный вызов с `account.id` (этап 8), иначе веб-кнопка снова станет неоднозначной.

### 4.3. Расписание

**Фильтры:** два bottom sheet: зал, преподаватель. Список опций — из несфильтрованной выборки дня/недели, с кэшем; «Все» сбрасывает. Выбор применяется сразу, без кнопки «Применить».

**Неделя:** 7 дней, сегодня — точка/активная плашка; стрелка вправо и свайп переводят на следующую неделю; выбранный день подсвечен. Переключение дня не сбрасывает фильтры.

**Карточки:**

- **Группа (`type 0`)**: название группы/стиля + уровень, зал, стикер (например «сампо»), строка замены красным, иконка группы. **Основные преподаватели** из `group.teacher1/2` показываются просто именами в формате **«Имя Фамилия», без отчества**; заменяющие из `widget_schedule/changes` — отдельной красной строкой «Замена: Имя Фамилия (вместо Имя Фамилия)».
- **Своё индивидуальное (`type 1`, `client.id == session.clientId`)**: имя клиента, преподаватель (`teacher`), зал, фиолетовый рельс. Если `teacher == null` — строки преподавателя нет.
- **Чужое индивидуальное (`type 1`, `client.id != session.clientId`)**: компактная серая строка: **только слово «индив» и название зала**. Ни ФИО, ни преподавателя, ни стиля, ни депозита.
- **Аренда (`type 2`)**: имя и фамилия арендатора в формате «Имя Фамилия», первое слово — `аренда`, а при стикере «сампо» (регистр любой) — `сампо`; зал показывается **последней строкой**. Преподаватель не выводится, если API его не дал в контексте аренды.

**Полный список дня** сортируется по `minutesBegin`, затем по типу (группа → индив → аренда), затем по названию. Никаких «показать ещё» внутри расписания: весь день — часть общего скролла.

**Пусто:** «На этот день занятий нет» + «Выбрать другой день». **Ошибка:** «Расписание не загрузилось» + «Повторить», фильтры и неделя остаются.

**Стикеры и замены:** `widget_schedule/stickers` и `widget_schedule/changes` на выбранный день; если методов нет/ошибка — карточки показываются без стикеров, без падения экрана.

#### FAB обновления (требование)

- Круглая кнопка **52 dp**, иконка обновления, правый нижний угол по умолчанию (16 от правого края, 96 от низа — над нижней навигацией).
- **Тап** — перезагрузить выбранный день (расписание + стикеры + замены), показать спиннер в кнопке; **drag** — переместить.
- Кнопка **никогда не выходит за safe area даже частично**. Границы: `12 ≤ x ≤ W − 12 − 52`, `statusBar + 12 ≤ y ≤ H − navHeight − 12 − 52`. Учитываются display cutout и системные insets.
- Позиция сохраняется между запусками; при смене размера/повороте (портрет) — повторный clamp. Кнопка не уезжает под нижнюю навигацию и не перекрывает статус-бар.
- Доступность: semantic label «Обновить расписание», зона 52 dp, haptic при перемещении; при drag не срабатывает обновление.
- Схема границ: [mockups/12-fab-spec.png](mockups/12-fab-spec.png).

### 4.4. Посещения

Заголовок: «Посещения», подпись «89 посещений».
Карточка: дата (`17.11.2026`), чип абонемента («Абонемент № 514» или «Разовое занятие»), название занятия/стиля, преподаватели, филиал с пином. Цветной рельс — по стилю. Для индивидуального посещения (`target.entity == teacher`) преподаватель показывается как «Имя Фамилия», без отчества.

### 4.5. Покупки

Заголовок: «Покупки», подпись «9 операций · оплата и пополнения».
Список по месяцам: заголовок месяца капсом, строки: дата `10.11`, описание (`typeText`), сумма зелёным, подпись «Картой · абонемент № 514» при наличии.

### 4.6. Записи

Заголовок: «Записи», подпись «1 запись».
Карточка: дата-бейдж (`23 НОЯ`), тип («Аренда зала», «Индивидуальное занятие»), зал, филиал, время, день недели, кнопка «Отменить запись» (outline red).
Под карточкой — правило отмены (не позднее 30 минут). Плашка «Хотите записаться?» скрыта: функциональность пока не нужна.
Данные: `widget_client_lk/schedule`; для регулярных занятий показываем ближайшее наступление; прошедшие — скрываем.
Отмена: только после подтверждения в bottom sheet; при ошибке — тост и возврат кнопки.

### 4.7. QR / штрихкод (лист)

По запросу QR-кнопка с главного экрана убрана; лист/`barcode` остаются в коде как задел на будущее и не отображаются в MVP.

### 4.8. Выход и истёкшая сессия

Выход — подтверждение в bottom sheet: «Выйти из кабинета?» → очистка secure storage, HTTP-кэша и состояния сессии, возврат на вход.
Истёкшая сессия/401 — мягкий переход на вход с сообщением «Сессия истекла, войдите снова». Кэш профиля очищается.

### 4.9. Меню и темы

**Меню `⋮`** — в шапке главной, справа от выхода. Поповер: «Тема оформления» (палитра) и «О приложении» (версия, Android 15+). Тап по «Тема оформления» открывает модальный диалог. В «О приложении» URL клуба кликабельный и открывается во внешнем браузере.

**Диалог тем** — 2×2 карточки с мини-превью:

| Тема | Характер | Расписание |
|---|---|---|
| Светлая | тёплый свет, розовый бренд | фон страницы |
| Тёмная «Графит» | графит, розово-фиолетовые акценты | тёмный фон |

Выбор применяется **сразу**, без перезагрузки; активная карточка с галочкой; кнопка «Готово» закрывает диалог. Тема сохраняется в `shared_preferences` (не секрет). Экран входа следует выбранной теме, как и остальное приложение.

## 5. Функциональные правила

### 5.1. Авторизация и передача сессии

```
1. App кодирует телефон алгоритмом виджета (base36 + 49680531 + reverse + base64).
2. POST widget_schedule/phone_info {phone} → count, ids, hasPassword.
3. Если count=0 — «Телефон не найден»; если hasPassword=0 — предложение восстановить пароль.
4. POST widget_schedule/check_password {phone, password} → success.
5. POST widget_client_lk/search {phone, socialPage:null}.
6. Декодирует обфусцированный ответ (XOR + split + base64) → {total, items:[client]};
   берёт items[0].id, items[0].secret и профиль.
7. Сохраняет client_id + secret в Android Keystore / iOS Keychain.
8. Открывает «Абонемент».
```

Fallback: при любой ошибке — сообщение в карточке, пароль очищается, фокус в поле;
сетевые ошибки предлагают «Повторить» (кнопка остаётся активной).

Проверка сессии при старте: `client_summary` или `accounts`; при ошибке доступа —
очистка и вход заново. Пароль не хранится и не логируется; после успешного
запроса вызывается `TextInput.finishAutofillContext(shouldSave: true)`, чтобы
Android Password Manager мог сохранить credential для приложения.

Из ответа `search` сохраняем только `items[0].id`, `items[0].secret` и поля профиля. Bcrypt-хеш `settings.password`, который вендор кладёт в тот же ответ, **отбрасываем сразу**: не пишем в модели, не кэшируем, не логируем.

**Честно о безопасности:** `secret` выдаётся вендором по одному телефону, поэтому он не является настоящим секретом. Нативный вход (D15) и Keystore защищают от случайного доступа на устройстве, но не от того, кто знает пароль. BFF **не планируется** (D10), поэтому это остаточный риск, который нужно проговорить владельцу клуба до релиза. Компенсации на устройстве: Keystore, запрет логов, `FLAG_SECURE` на чувствительных экранах, HTTPS, minSdk 35.

### 5.2. Время и даты

- Часовой пояс клуба: `branch.options.timezoneOffset = 420` (UTC+7). Все даты и дни недели считаем в поясе клуба, а не устройства.
- `minutesBegin`/`minutesEnd` — уже локальное время клуба в минутах от полуночи; форматируем `HH:mm`.
- Unix-даты (`date`, `dateBegin`, `visitDate`, `created`) переводим в пояс клуба.
- Русские месяцы в родительном падеже: «19 ноября», «7 февраля 2027 г.», день недели «четверг».
- «Сегодня» определяется по поясу клуба; неделя начинается с понедельника.

### 5.3. Правило индивидуальных занятий (ключевое)

Входные данные: `item.type == 1`, `item.client`, `item.teacher`, `item.hall`, `session.clientId`.

| Условие | Заголовок | Вторая строка | Третья строка | Вид карточки |
|---|---|---|---|---|
| `client.id == clientId` | ФИО клиента (`lastName name`) | преподаватель (`teacher.lastName name`), если есть | зал | полная, фиолетовый рельс |
| `client.id != clientId` | `индив` | — | зал | компактная серая |
| `client == null` (аномалия) | `индив` | — | зал | компактная серая |

Важно: для чужого занятия **не показываем** ни ФИО, ни преподавателя, ни стиль, ни депозит/бонусы, даже если они пришли в ответе. Эти поля не попадают в модель UI и не логируются. `client.id` сравниваем как int.

Время и длительность остаются у всех карточек — это атрибут сетки, а не персональные данные. Формулировка «просто слово „индив“ и зал» относится к содержательной части: без ФИО, преподавателя, стиля и депозита; время/длительность показываем, иначе занятие невозможно найти в дне.

### 5.4. Аренда

| Условие | Заголовок | Вторая строка | Вид |
|---|---|---|---|
| любая аренда | «Имя Фамилия» арендатора, первое слово `аренда`/`сампо` | зал последней строкой | полная |
| если стикер `сампо` | первое слово `сампо` вместо `аренда` | зал последней строкой | полная |

Имя арендатора показывается и для чужой аренды — это явное решение владельца
продукта от 20.11.2026 (перекрывает прежнюю приватную схему D4). Стикер «сампо»
проверяется без учёта регистра; при нём чип стикера не дублируется.

### 5.5. Группы

- Заголовок: `group.style.name` + `group.level` (например, «Бачата База 2.0»); если группы нет — `style.name` или «Групповое занятие».
- Зал: `hall.name` (в API приходит «Большой зал», «Средний», «Малый»).
- Основные преподаватели: `group.teacher1` + `group.teacher2` (оба, если есть) → просто имена в формате «Имя Фамилия», без `middleName` и без слова «Основные».
- Замена: `widget_schedule/changes` → «Замена: Имя Фамилия (вместо Имя Фамилия)» красным; замена показывается вместе с основным составом, без отчества.
- Стикер: из `widget_schedule/stickers` по `schedule.id`; «сампо» — жёлтый.

### 5.6. Кэш и обновление

- Расписание дня: кэш 5 минут, ключ = день + фильтры; при возврате на день — мгновенный показ кэша и фоновое обновление. FAB и pull-to-refresh сбрасывают кэш дня.
- Абонементы/профиль: 60 секунд; после заморозки/возврата из веб-сценария — сброс.
- Посещения/покупки: страницы по 20, кэш 5 минут, pull-to-refresh.
- Офлайн: показываем последний кэш с плашкой «Нет соединения · данные могут быть неактуальны»; запись/отмена недоступны.

### 5.7. Ошибки

| Код/ситуация | Что видит клиент |
|---|---|
| Нет сети | Плашка «Нет соединения», кэш, «Повторить» |
| 401 / `LogicException` доступа | «Сессия истекла», очистка, вход |
| 500 вендора | «Сервис клуба временно недоступен», «Повторить», без стека |
| Пустой список | Empty state с действием |

Технические тексты вендора (стеки, пути) не показываем и не логируем в релизе.

### 5.8. Тема оформления

- `ThemeController` хранит выбор в `shared_preferences` (`light | dark | pink | system`), по умолчанию — `light`.
- Смена темы применяется сразу, без перезапуска; диалог показывает активную тему галочкой.
- `system` слушает `MediaQuery.platformBrightness`; при смене системной темы приложение переключается без потери состояния.
- Фон расписания — часть темы (D11); отдельной настройки нет.
- Экран входа следует выбранной теме (нативный, D15), как и остальное приложение.
- Тема не секрет, не шифруется; в логах только имя темы.

### 5.9. HTTP-клиент: профиль мобильного Chrome

Решение: нативные запросы к `widget_client_lk/*` **мимикрируют под мобильный Chrome**, а **версия Chrome берётся с устройства клиента**. Профиль заголовков снят с живой сессии Chrome 156 mobile 19.11.2026; версия в UA — динамическая, из установленного Chrome.

| Заголовок | Значение |
|---|---|
| `User-Agent` | `Mozilla/5.0 (Linux; Android 10; K) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/<major>.0.0.0 Mobile Safari/537.36` — reduced-UA Chrome, `<major>` с устройства |
| `Accept` | `application/json, text/plain, */*` |
| `Accept-Language` | из `PlatformDispatcher.locales`, например `ru-RU,ru;q=0.9,en-US;q=0.8,en;q=0.7`; fallback `ru-RU` |
| `Content-Type` | `application/json` |
| `Origin` | `https://<tenant>` (из `AppConfig.baseUrl`, без слэша) |
| `Referer` | `https://<tenant>/widget/2` (виджет из конфига) |
| `Sec-Fetch-Site` | `same-origin` |
| `Sec-Fetch-Mode` | `cors` |
| `Sec-Fetch-Dest` | `empty` |
| `Sec-CH-UA` | `"Not:A-Brand";v="8", "Chromium";v="<major>", "Google Chrome";v="<major>"` — low-entropy; GREASE-бренд по таблице/алгоритму Chromium (для 156 — `Not:A-Brand` v8) |
| `Sec-CH-UA-Mobile` | `?1` |
| `Sec-CH-UA-Platform` | `"Android"` |
| `Priority` | `u=1, i` |
| `Accept-Encoding` | `gzip, deflate, br, zstd` — с Brotli/Zstd-декодерами |

**L2 — выбранный уровень.** Client Hints, полный `Accept-Encoding`, языки устройства и `Priority` добавлены. High-entropy hints (`Sec-CH-UA-Full-Version-List`, `Sec-CH-UA-Model`, `Sec-CH-UA-Platform-Version`) **не отправляем** — Chrome шлёт их только по `Accept-CH`. Если major нет в таблице GREASE, `Sec-CH-UA` не отправляем вовсе: отсутствие hint лучше неверного бренда; таблица обновляется с релизами.

**Как определяется версия:**

1. `PackageManager.getPackageInfo("com.android.chrome", 0).versionName` → major (`156.0.8078.80` → `156`). Только stable-пакет Chrome.
2. Если Chrome не установлен/отключён/версия не парсится — версия системного WebView: `WebView.getCurrentWebViewPackage()?.versionName` (Chromium-движок), major.
3. Если недоступно и это — `defaultChromeMajor` из конфига (на старте проекта `156`, обновляется с релизами).
4. Версия кэшируется на холодном старте и при возврате из фона; первый API-запрос ждёт результата (сплэш/инициализация).

Для доступа к пакетам на Android 11+ в `AndroidManifest.xml` нужен `<queries>` **только** для Chrome/WebView:

```xml
<queries>
  <package android:name="com.android.chrome" />
  <package android:name="com.google.android.webview" />
  <package android:name="com.android.webview" />
</queries>
```

Не перечисляем все установленные приложения — только эти пакеты. `chromeVersionSource` (`chrome` / `webview` / `default`) пишем в debug-лог, но не отправляем на сервер.

**Не отправляем:** `Cookie`/`PHPSESSID` (в живой сессии для этого API их не было; клиент cookie-less), `X-Requested-With`, `Authorization`, high-entropy Client Hints (`Full-Version-List`, `Model`, `Platform-Version`), телефон/ФИО/`client_id` в UA, Android ID/IMEI/MAC. Токен `wv` в UA не добавляем: это нативный API-клиент, а не WebView.

**Почему так:** вендор видит обычный мобильный Chrome актуальной версии, как на телефоне клиента, и не выделяет приложение по UA/заголовкам; авторизация остаётся `client_id` + `secret` в JSON-теле.

**Ограничения:** мимикрия на уровне HTTP-заголовков. TLS/JA3, HTTP/2-фрейминг и тайминги остаются нативными (Dio/OkHttp), а не Chrome. L2 требует реальных Brotli/Zstd-декодеров: без них нельзя заявлять полный `Accept-Encoding`. Если вендор включит строгий bot-protection по TLS-отпечатку, понадобится реальный Chrome Custom Tabs/WebView или BFF — в текущем объёме этого нет.

**WebView в auth больше не используется (D15).** Всё, что выяснено про вендорский WebView, его UA/VK-ветку, CSS-кастомизацию, скорость и autofill, собрано в [WEBVIEW-NOTES.md](WEBVIEW-NOTES.md). Решение D13 (desktop-UA страницы входа) сохранено как историческое: для будущих web-сценариев (заморозка/оплата/QR) его нужно перепроверить. Native API остаётся mobile L2.

Проверка API: `accounts` отвечает `200` и с native-UA, и с Chrome-UA + `Origin`/`Referer`, и вовсе без `User-Agent`; выбор профиля — продуктовое решение, а не требование вендора.

### 5.10. Полная мимикрия: что ещё выдаёт native-клиент

Заголовки — только первый слой. Даже с точным Chrome-UA остаются отличия:

| Слой | Что выдаёт | Как закрыть |
|---|---|---|
| Client Hints | Chrome шлёт `Sec-CH-UA`, `Sec-CH-UA-Mobile`, `Sec-CH-UA-Platform`; **L2**: low-entropy добавлены, GREASE-бренд должен совпадать с major | High-entropy не слать; GREASE — из таблицы/алгоритма Chromium |
| Сжатие | Chrome: `gzip, deflate, br, zstd`; **L2**: заявляем полный набор | Brotli/Zstd-декодеры + тест на каждый `Content-Encoding` |
| Язык | Chrome берёт языки устройства; **L2**: строим из `PlatformDispatcher.locales` | Fallback `ru-RU`, q-values как у Chrome |
| Порядок/состав заголовков | Chrome имеет свой порядок и `Priority: u=1, i`; Dio/OkHttp могут отличаться | Задать порядок вручную; `Priority` уже в профиле |
| Cookie | Браузер может иметь cookies сессии; native — cookie-less | На этом API cookie не было; если появятся — общий CookieJar с WebView |
| TLS | Chrome ClientHello: JA3/JA4, cipher suites, GREASE, ALPN; Dart/OkHttp — другие | Только Chromium network stack: WebView `fetch` или Cronet |
| HTTP/2 | SETTINGS, WINDOW_UPDATE, priority, header order у Chrome свои | Chromium network stack (WebView/Cronet) |
| Поведение | Chrome переиспользует соединения, не долбит параллельно, соблюдает тайминги | Keep-alive, ограничить параллелизм, не ретраить агрессивно |
| WebView-движок | WebView UA можно подменить, но `navigator.userAgentData`/TLS остаются версией WebView | Для полного совпадения — API-вызовы из самого WebView |

**Уровни:**

1. **L1 — заголовки** (база): UA, Accept, Language, Origin/Referer, Sec-Fetch, cookie-less.
2. **L2 — выбран**: L1 + low-entropy Client Hints + `br/zstd` + языки устройства + `Priority`. TLS/HTTP2 всё ещё native, но заголовочный профиль близок к Chrome.
3. **L3 — Chromium network stack**: все вызовы `widget_client_lk/*` идут через `fetch` в WebView (same-origin, Chrome-UA, cookies, TLS/HTTP2 WebView) или через Cronet. Единственный практичный способ закрыть TLS/HTTP2; цена — WebView должен быть жив, запросы идут через JS-bridge, сложнее кэш/ошибки/фон.

**Решение:** берём **L2**. L3 оставляем как переключаемый `WebViewApiClient` на случай WAF; если вендор включит строгий TLS/JA3-бот-контроль, без L3 не обойтись.

## 7. Доступность и Android 15

- Edge-to-edge: фон под системными панелями, контент в `SafeArea`; нижняя навигация учитывает gesture inset.
- Predictive back: из WebView — назад по истории; из листов — закрытие; с главной — выход с подтверждением? Нет, на главной back сворачивает приложение.
- Минимальные зоны 48 dp; контраст текста ≥ 4.5:1 (muted на белом — 3.6:1, только для второстепенных подписей ≥ 12 px; для важного — `ink-2`).
- Масштаб шрифта 1.3: карточки не обрезают заголовок, допускают 2 строки; время не переносится.
- TalkBack: карточка читается как «12:00, 60 минут, Анна Смирнова, преподаватель Андрей Чистяков, Средний зал»; для чужого «индив» — «12:00, индивидуальное занятие, Средний зал».
- Не передавать смысл только цветом: «замена» — текст, «аренда» — слово.
- Обе темы проверяются на контраст: основной текст ≥ 4.5:1, крупные заголовки ≥ 3:1; в тёмной теме активный день — светлая плашка с тёмным текстом.
- FAB: semantic label «Обновить расписание», стандартный drag; для TalkBack — custom action «Сбросить позицию»/«Переместить в угол», чтобы кнопка не была недоступна без жеста. При `reduce motion` — без анимации перелёта.
- Android 15: 16 KB page size (проверить на релизной сборке), themed icon (monochrome), splash screen, `targetSdk 35`.
