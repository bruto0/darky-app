# impulseCRM × Android: авторизация — рабочий пакет (handoff)

Дата сбора: **2026-11-19**. Контур: `https://4621c03198bd6735334088.impulsemini.ru`
(тенант impulseCRM, «D'arky Dance»).

Эта папка — самодостаточный передаточный комплект: всё, что выяснено про авторизацию в
этой системе, чтобы продолжить разработку Android-приложения в другом воркспейсе, не
повторяя реверс-инжиниринг. Внутри нет паролей, API-ключей и персональных данных —
только адреса, форматы запросов, проверенные факты и скрипты.

## 1. Что за система

impulseCRM — SaaS для фитнес-клубов, танцевальных студий и салонов. У тенанта один домен,
но **две разные аудитории с разными механизмами входа**:

| Аудитория | Точка входа | Механизм | Документ |
|---|---|---|---|
| Сотрудники клуба | `/login` | `POST /api/public/user/login` (form-urlencoded) → PHP-сессия, передаётся как `?PHPSESSID=<sid>` | [android-auth.md](android-auth.md) |
| Клиенты клуба | `/widget/2` | телефон → объект клиента с `secret`; все запросы подписываются `client_id` + `secret` | [widget-auth.md](widget-auth.md) |

Публичный REST API (`/api/public/<сущность>/<действие>`, 109 операций — справочник в
[../impulsecrm-api/](../impulsecrm-api/README.md)) авторизует **только** по персональному
API-ключу: `Authorization: Basic <API_KEY>`. Ни сессия сотрудника, ни клиентский `secret`
к нему не подходят (проверено, `401`).

## 2. Главные выводы

1. **Страница логина сотрудника — тонкая обёртка** над `POST /api/public/user/login`
   (`username`/`password`, form-urlencoded). Ни капчи, ни CSRF, ни cookie не требуется —
   логин воспроизводится из `curl`. Сессия — PHP-сессия, которую веб-версия передаёт
   query-параметром `?PHPSESSID=`.
2. **Виджет `/widget/2` — личный кабинет клиента**, а не сотрудника. «Пароль» там
   декоративный: `widget_client_lk/search` по одному номеру телефона отдаёт `client_id`
   и `secret`, которыми подписываются все запросы ЛК, **а также bcrypt-хеш пароля** и
   персональные данные. Это обход аутентификации на стороне вендора.
3. **Поэтому нельзя строить защиту приложения на `secret`** — он не является секретом.
   Если нужен нативный UX — перед API ставится свой BFF, который держит `secret` у себя.
4. **Задокументированный API с клиентскими кредами недоступен** (только с API key).
   Клиентский периметр — это недокументированные `widget_client_lk/*`,
   `widget_client_mobile/*` и `widget_schedule/*`.
5. **Общее расписание публично**: `widget_schedule/list` и `widget_client_mobile/schedule`
   отдают сетку занятий без всякой авторизации, вместе с ФИО и депозитами клиентов,
   записанных на индивидуальные занятия и аренду.

## 4. Быстрый старт

Требования: Windows PowerShell 5.1 или PowerShell 7, `curl.exe` (входит в Windows 10+).
Скрипты сохранены в UTF-8 с BOM — так их читает и PowerShell 5.1.

```powershell
cd docs\mobile-auth

# 1) Вход сотрудника: пароль спрашивается интерактивно, в отчёт не попадает
powershell -File .\check-auth.ps1 -BaseUrl https://<tenant>.impulsemini.ru -Username +7XXXXXXXXXX

# 2) Вход клиента в виджет: печатает ответы phone_info и check_password
powershell -File .\widget-probe.ps1 -BaseUrl https://<tenant>.impulsemini.ru `
    -Phone +7XXXXXXXXXX -Password '<пароль>'

# 3) Что доступно клиентским кредам (нужен телефон клиента, пароль не нужен)
powershell -File .\widget-surface.ps1 -BaseUrl https://<tenant>.impulsemini.ru -Phone +7XXXXXXXXXX
```

Учётные данные **не хранятся в репозитории**: передаются параметрами (или через
`$env:CHECK_AUTH_PASSWORD` / `$env:CHECK_AUTH_API_KEY` для `check-auth.ps1`). Для CI
заведите отдельного тестового клиента/сотрудника и удалите его после проверок.

## 5. Что проверено и чем

Все факты получены на живом контуре 2026-11-19 и зафиксированы в
[findings.json](findings.json) и в таблицах соответствующих документов.

- **Сотрудник:** логин из `curl` без cookie/CSRF (`403` с осмысленным `message`),
  `user/current` без сессии → `401`, CORS отражает любой `Origin`, 5 неудачных попыток
  подряд не блокируются.
- **Клиент:** `widget/load/2` без авторизации; `phone_info` → `{count, ids, hasPassword}`;
  `check_password` → `{success}`; `search` → профиль + `secret` + bcrypt-хеш; чтение ЛК
  (`accounts`, `visits`, `deposits`, `bonuses`, `debts`, `reservations`, `barcode`,
  `all_levels`, `product_sections`, `news`, `stories`, `client_summary`,
  `widget_client_mobile/summary`) с `{client_id, secret}`.
- **Расписание:** `widget_client_lk/schedule` — только занятия клиента (1 запись);
  `widget_schedule/list` и `widget_client_mobile/schedule` — общая сетка (93 записи за
  14 дней), **без кредов**, с ФИО/депозитами в записях типов 1 и 2.
- **Закрыто:** документированный API с `secret` (`401`), админские `widget/*`,
  `widget_pbx/*`, `widget_chat/*` (`401`).

## 6. Рекомендация по приложению

| Сценарий | MVP (быстро) | Продакшен (правильно) |
|---|---|---|
| Приложение **для клиентов** | W1: WebView с `/widget/2` | W3: BFF + свой JWT, `secret` на сервере |
| Приложение **для сотрудников** | A: нативный логин `user/login` | D: BFF + свой JWT, API key на сервере |

Подробно — [architecture.md](architecture.md). Ключевое правило: **в APK не должно быть
ни API-ключа клиента, ни клиентского `secret`** — оба дают доступ к чужим данным.

## 7. Ближайшие шаги

1. **Определиться с аудиторией** приложения (клиенты или сотрудники) — от этого зависит
   весь контур авторизации.
2. **Согласовать с владельцем CRM/вендором** использование внутренних методов
   (`user/login`, `widget_client_lk/*`): они недокументированы и могут измениться.
3. **Отправить [vendor-report.md](vendor-report.md)** вендору — часть рисков снимается
   только на его стороне (выдача `secret` по телефону, хеш пароля, публичные ПДн).
4. **Поднять BFF-заглушку** и контрактные тесты на фикстурах из [findings.json](findings.json),
   чтобы приложение не зависело от живого контура.
5. Реализовать выбранный вариант (W1/W3 или A/D), закрыть [open-questions.md](open-questions.md).

## 8. Перенос в другой воркспейс

Что скопировать:

- `docs/mobile-auth/` — этот пакет (документы + скрипты, ~140 КБ);
- `docs/impulsecrm-api/` — справочник по документированному API (23 сущности, 109 операций).

Что передать **отдельно**, не через репозиторий: телефон и пароль тестового клиента,
телефон и пароль тестового сотрудника, API-ключ контура (если понадобится). Скрипты
принимают их параметрами, поэтому в коде и документах они не нужны.

Что проверить на новом месте:

1. `powershell -File .\widget-probe.ps1 -Phone ... -Password ...` — вход в виджет работает.
2. `powershell -File .\check-auth.ps1 -BaseUrl ... -Username ...` — вход сотрудника.
3. Сверить ответы с [findings.json](findings.json). Если вендор обновил продукт — расхождения
   будут видны сразу (особенно в обфускации ответов и в наборе полей расписания).

Зависимостей нет: Windows PowerShell 5.1+/PowerShell 7 и `curl.exe`. Скрипты сохранены в
UTF-8 с BOM, чтобы 5.1 читал кириллицу.

## 9. Ограничения и безопасность

- Не коммитить пароли, `secret`, API-ключи; в примерах — только заглушки.
- Не хранить пароль пользователя на устройстве; сессия/токен — в
  `EncryptedSharedPreferences`/Keystore.
- `secret` клиента не считать секретом: он выдаётся по телефону. Единственный способ
  сделать его защищённым — держать на сервере (BFF).
- Использование внутренних эндпойнтов — риск блокировки/претензий; нужно письменное
  согласие вендора. Персональные данные клиентов — 152-ФЗ.
- Данные тестового клиента (ФИО, абонементы, посещения) в документах не публикуются.
