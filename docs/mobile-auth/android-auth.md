# Авторизация пользователя в Android-приложении поверх impulseCRM

Дата: 2026-11-19. Контур: `https://4621c03198bd6735334088.impulsemini.ru` (тенант impulseCRM).
Справочник по REST API этой же системы: [../impulsecrm-api/README.md](../impulsecrm-api/README.md).

> **Это документ про вход сотрудника** (страница `/login`, эндпойнт `user/login`).
> Если приложение — для клиентов клуба (личный кабинет), контур другой:
> [`/widget/2` → client_id + secret](widget-auth.md).
>
> Весь пакет документов и порядок работы — в [README.md](README.md).


## 0. Главное

1. **Страница логина не нужна.** Она сама ходит в обычный HTTP-эндпойнт
   `POST /api/public/user/login` с телом `username=<телефон>&password=<пароль>` и получает
   идентификатор PHP-сессии. Капчи, CSRF-токена и обязательных cookie там нет — запрос
   воспроизводится из `curl`.
2. **Сессия — это `PHPSESSID`, который вся веб-версия передаёт не cookie, а query-параметром**
   `?PHPSESSID=<sid>` к каждому запросу `/api/public/...`. Тот же приём может использовать
   мобильное приложение.
3. Значит, есть три принципиально разных пути: **воспроизвести логин нативно** (лучший UX),
   **подсмотреть сессию в WebView** (устойчивее к изменениям страницы) и **спрятать всё
   за своим бэкендом** (единственный вариант, пригодный для продакшена с чужими ключами
   и паролями).
4. **Ключ клиента нельзя зашивать в APK.** Он даёт доступ ко всей CRM клиента, извлекается
   из apk за минуту, а CORS у API открыт (`Access-Control-Allow-Origin` отражает любой
   источник) — то есть ключом можно пользоваться откуда угодно. В приложении должны быть
   только «пользовательские» креденшелы: сессия или собственный токен вашего бэкенда.

## 1. Что проверено на живом контуре

| Что проверялось | Как | Результат |
|---|---|---|
| Страница `/login` | `GET` | 200, Vue 2 SPA (webpack), форма «Имя пользователя / Пароль», без капчи |
| Эндпойнт логина | найден в `chunk-8576d1ca` (`pages/Login.vue`) | `POST /api/public/user/login`, тело `username=…&password=…` (`x-www-form-urlencoded`) |
| Логин из `curl`, без cookie/CSRF/Referer | `curl -d 'username=…&password=…'` | работает: `403 {"message":"Пользователь не найден."}` для несуществующего пользователя |
| Пустой/битый логин | `{}`, `text/plain` | `403 {"message":"Укажите логин."}` — значит, разбор тела идёт только для form-urlencoded |
| Контракт успеха | по коду `Login.vue` | `{"success": true, "session": "<sid>"}`; при `success=false` — `message` (иногда HTTP 200, иногда 403) |
| Передача сессии | по коду `app~ea1f58e8` (`c151`) | `localStorage.impulsecrm_session` → `?PHPSESSID=<sid>` в каждом запросе |
| Проверка сессии | `GET /api/public/user/current` без сессии | `401 {"message":"Требуется аутентификация"}` |
| CORS | `OPTIONS` с `Origin: https://example.com` | `Access-Control-Allow-Origin: https://example.com`, методы и заголовки разрешены |
| Ограничение попыток | 5 неудачных попыток входа подряд | ответ не меняется, `429`/капчи нет (проверено на несуществующем логине — берегите реальные учётки) |
| Встроенный «magic link» | по коду `Login.vue` | `/login?auth=<base64>` → страница сама подставляет логин/пароль и логинится |
| Тот же эндпойнт на `demo.impulsecrm.ru` | `POST user/login` с несуществующим логином | `403 {"message":"Пользователь не найден."}` — механизм продуктовый, а не самоделка тенанта |

Дополнительно, из официального справочника API: у сущности `user` есть поля
`apiToken` («API токен пользователя») и `password` («Хеш пароля»), а `user/update`
позволяет эти поля задавать. То есть **персональный токен на пользователя в системе
предусмотрен** — вопрос лишь в том, отдаёт ли его ваш ключ и ваша роль. Это первый
пункт, который надо проверить живьём (см. §8).

## 2. Ограничения, из которых растут варианты

- **Один ключ клиента** на всё API. Даже если технически он «привязан к пользователю»,
  это один конкретный пользователь, а не каждый сотрудник, поэтому:
  - права в API — «права того пользователя, от которого выпущен ключ»;
  - положить его в приложение = отдать весь тенант любому, кто распакует apk;
  - разграничить сотрудников на стороне CRM, используя только этот ключ, нельзя.
- **Логин = телефон**, пароль проверяет только сервер. Хэши (`password`) в API есть, но
  полагаться на них нельзя: формат/доступность не гарантированы, а реализовывать
  `password_verify` (bcrypt/argon2) у себя — значит дублировать чужую криптографию.
- **Сессия — PHP-сессия**, а не JWT: у неё есть TTL и сборщик мусора, продления «из
  коробки» нет (в API есть `user/refresh_token`, но его семантика не проверена).
- **Внутренний эндпойнт недокументирован**: `user/login` нет в официальном справочнике
  (`/api/public/api_doc/load/ru`), он может измениться без предупреждения.

## 3. Варианты

### Вариант A. Нативный логин тем же эндпойнтом (рекомендуется как MVP)

Приложение само делает `POST /api/public/user/login`, получает `session`, хранит его
в защищённом хранилище и дальше ходит в API с `?PHPSESSID=<session>`.

```
┌────────────┐  username/password   ┌──────────────────────────────┐
│  Android   │ ───────────────────► │ POST /api/public/user/login  │
│            │ ◄─────────────────── │ {success, session}           │
│            │                      └──────────────────────────────┘
│            │  GET /api/public/... ?PHPSESSID=<session>  ──────────►
└────────────┘
```

**Плюсы:** нативный UX (одно поле телефона, автозаполнение, биометрия, «запомнить»),
нет WebView и его ограничений, легко тестировать (`MockWebServer`), полный контроль над
ошибками и аналитикой.

**Минусы:** опирается на недокументированный эндпойнт; при появлении капчи/2FA/лимита
попыток ломается; сессию надо продлевать самому; в APK нет ключа — значит, либо сессии
достаточно для всех вызовов (проверить!), либо нужен бэкенд (вариант D).

**Когда подходит:** пилот, внутреннее приложение, доступ к API только через сессию
пользователя.

### Вариант B. WebView-логин с извлечением сессии

Показываем настоящую страницу `/login` в `WebView`, после успешного входа читаем
`localStorage.impulsecrm_session` через `evaluateJavascript` (или cookie через
`CookieManager`), сохраняем и дальше работаем нативно.

**Плюсы:** страницу сопровождает вендор — капча, 2FA, смена полей, «Забыли пароль?»
появляются сами; пароль не проходит через ваш код; минимум работы при изменениях.

**Минусы:** UX (браузерная вёрстка, зум, клавиатура), риск фишинга и требования
Google Play к вводу паролей, сложно надёжно поймать момент успеха (SPA меняет URL
через `history.pushState`, `onPageFinished` при этом не всегда срабатывает — нужен
`doUpdateVisitedHistory` или периодический опрос), сессия может быть привязана к
User-Agent/кукам WebView, легко получить «залипшее» состояние.

**Когда подходит:** если у вендора появится капча/2FA, или как аварийный фолбэк к A.

### Вариант C. WebView только как «добытчик сессии», дальше — нативные вызовы

Уточнение B: WebView живёт один экран, после получения `session` уничтожается
(`webView.destroy()`), все данные грузятся нативным HTTP-клиентом. Сессия одна и та же,
поэтому это не «два приложения», а «страница логина как есть + нативный клиент».

Практически это самый устойчивый гибрид: всё, что касается пароля/капчи, отдаём
странице; всё, что касается данных, — своему коду.

### Вариант D. BFF / auth-proxy на своём бэкенде (рекомендуется для продакшена)

Приложение общается только со своим сервером; сервер хранит ключ клиента, логинится за
пользователя и проксирует вызовы.

```
Android ──phone+password──► BFF ──POST user/login──► CRM
        ◄──JWT(access+refresh)── BFF ◄──session────── CRM
Android ──Bearer JWT──► BFF ──?PHPSESSID=…──► CRM /api/public/...
```

**Плюсы:**

- ключ клиента не покидает сервер;
- можно добавить свою 2FA, биометрию, ограничение попыток, аудит «кто что смотрел»;
- можно кэшировать, склеивать ответы, добавлять офлайн-режим;
- при смене API/появлении капчи правится только бэкенд, приложение не обновляется;
- можно выдавать свои роли и не показывать сотруднику лишние разделы.

**Минусы:** нужен сервер (и его эксплуатация), пароль транзитно проходит через ваш
бэкенд (нужны HTTPS, отсутствие логов тела, шифрование в памяти), ответственность за
персональные данные, юридические отношения с вендором.

**Важно:** сервер не должен хранить пароль. Храните только сессию (Redis, TTL) и свой
refresh-токен; при истечении сессии просите пароль заново или используйте
`user/refresh_token`.

### Вариант E. BFF + персональные `apiToken` (максимально «по документации»)

Если ваш ключ видит `user/load` и отдаёт `apiToken`, можно вообще не использовать
сессию для данных:

1. BFF проверяет телефон+пароль через `user/login` (или `user/load` + сверка хэша);
2. BFF достаёт `apiToken` этого пользователя (`GET /api/public/user/load/{id}` с ключом
   клиента) или выпускает новый (`user/update` с `apiToken`);
3. приложение ходит в CRM от имени конкретного сотрудника — либо напрямую с
   `Authorization: Basic <apiToken>`, либо через BFF, который подставляет этот токен
   (первый вариант быстрее, второй — безопаснее: токен не попадает на устройство).

**Плюсы:** используется только документированный API; права сотрудника обеспечивает
сама CRM; сессия PHP не нужна; токен можно отозвать (`user/update`), не меняя пароль.

**Минусы:** `apiToken` в приложении — это фактически постоянный пароль (нужен короткий
срок жизни и привязка к устройству); надо проверить, что ключ действительно видит
`apiToken` и что CRM принимает его как авторизацию (по документации — да, §«API-ключ»);
при смене ключа «Обновить ключ» в вебе старые токены ломаются.

### Вариант F. «Magic link» `?auth=…`

Страница умеет автологин по ссылке: параметр `auth` — это base64 от строки
`username;password`, записанной задом наперёд (получается `drowssap;emanresu` для
`username;password`), причём символы `=` заменены на `%`. BFF может сформировать такую
ссылку и открыть её в Custom Tabs/WebView — пользователь попадает в систему без ввода
пароля.

**Плюсы:** ноль работы на клиенте, ровно тот флоу, который поддерживает вендор.

**Минусы:** пароль оказывается в URL (история, логи прокси, `Referer`), ссылка
одноразовостью не обладает — это скорее «служебный» механизм, чем способ авторизации
пользователя. Для продакшена — нет; для демо/стенда — можно.

### Вариант G. Официальный путь: попросить у вендора доступ

Это не «вариант интеграции», а способ убрать все риски выше:

- персональные API-токены на сотрудника (в системе они уже есть);
- OAuth2 (authorization code + PKCE) или SSO/SAML для мобильного клиента;
- либо официальный мобильный API: в системе есть контур `widget_client_mobile/*`,
  `widget_client_lk/*` — это API клиентских приложений, со своей авторизацией по
  телефону. Если ваше приложение — для клиентов, а не для сотрудников, начинать надо
  именно с него, а не с логина сотрудника.

Даже если ответ будет «нет», письменное подтверждение «использовать `user/login` можно»
снимает главный риск — блокировку/претензии.

### Антипаттерны (не делать)

- **Хранить пароль в приложении** («чтобы не логиниться каждый раз») — при утечке apk
  или бэкапа это все пароли сотрудников.
- **Зашивать ключ клиента в APK** — это доступ ко всей CRM, включая клиентскую базу.
- **Один «сервисный» пользователь + разграничение прав на клиенте** — любой, кто
  декомпилирует приложение, получает полные права.
- **Логин «через страницу» парсингом HTML** — страница SPA, HTML пустой; парсить нечего,
  всё равно придётся либо выполнять JS, либо дергать эндпойнт.
- **Проверять пароль по хэшу на клиенте** — хэш в приложении = офлайн-брутфорс.

## 5. Рекомендация

1. **MVP / пилот (1–2 дня):** вариант A. Он проверен: эндпойнт отвечает, контракт
   известен, WebView не нужен.
2. **Прод:** вариант D (BFF), при возможности — в связке с E (персональные `apiToken`),
   чтобы данные ходили по документированному API, а не по сессии.
3. **Фолбэк:** C — если вендор включит капчу или 2FA. Экран логина тогда — тот же
   WebView, остальное не меняется: интерфейс `AuthRepository` один и тот же.
4. Параллельно — письмо вендору (G): персональные токены/OAuth. Это единственный путь,
   который не сломается при следующем обновлении продукта.

Ключевое архитектурное правило: **в приложении не должно быть ключа клиента**, а экран
логина должен быть заменяемым — `interface AuthRepository { suspend fun login(phone, password): Session }`
с двумя реализациями (native / webview), выбор — фича-флагом.

## 6. Детали реализации (Android)

### 6.1. Нативный логин (вариант A)

```kotlin
class ImpulseAuthApi(
    private val baseUrl: HttpUrl,          // https://<tenant>.impulsemini.ru
    private val client: OkHttpClient,
) {
    suspend fun login(username: String, password: String): Session = withContext(Dispatchers.IO) {
        val body = FormBody.Builder()
            .add("username", username.trim())   // телефон в том виде, в каком он в CRM
            .add("password", password)
            .build()

        val request = Request.Builder()
            .url(baseUrl.newBuilder().addPathSegments("api/public/user/login").build())
            .post(body)
            .header("Accept", "application/json")
            .build()

        client.newCall(request).execute().use { response ->
            val text = response.body?.string().orEmpty()
            val json = runCatching { JSONObject(text) }.getOrNull()
                ?: throw AuthException("Некорректный ответ сервера (${response.code})")

            // Внимание: 403 приходит и на ошибку логина — не трактуйте его как «нет прав».
            if (!response.isSuccessful || !json.optBoolean("success")) {
                throw AuthException(json.optString("message", "Не удалось войти"), response.code)
            }
            Session(json.getString("session"), json.optJSONObject("user")?.toString())
        }
    }
}
```

Подстановка сессии — интерсептором, чтобы не забыть ни в одном вызове:

```kotlin
class SessionInterceptor(private val store: SessionStore) : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val session = store.session ?: return chain.proceed(chain.request())
        val url = chain.request().url.newBuilder()
            .addQueryParameter("PHPSESSID", session)   // так делает веб-версия
            .build()
        return chain.proceed(chain.request().newBuilder().url(url).build())
    }
}
```

Проверка сессии на старте — `GET /api/public/user/current`:
`200` → пускаем в приложение, `401` → экран логина.

### 6.2. Хранение

- `EncryptedSharedPreferences` (Jetpack Security) или ключ в Android Keystore +
  зашифрованный файл; `android:allowBackup="false"` для этих данных.
- Хранить: `session`, `userId`, `username`, время логина. **Пароль — не хранить.**
- На экране ввода пароля — `FLAG_SECURE`, отключить автозаполнение пароля системой,
  если политика этого требует; лог — без тела запроса.

### 6.3. Обработка ошибок и жизненный цикл

- `403 {"message": …}` при логине → показать текст как есть (там русские сообщения:
  «Укажите логин.», «Пользователь не найден.»).
- `401 {"message":"Требуется аутентификация"}` на любом вызове → сессия истекла:
  чистим хранилище, ведём на логин, показываем причину.
- Продление: попробовать `POST /api/public/user/refresh_token` (есть в веб-клиенте) и
  посмотреть, продлевает ли он сессию; если нет — либо TTL сессии достаточный, либо
  вариант D с refresh-токеном на своей стороне.
- «Выйти на всех устройствах» — `POST /api/public/user/logout_devices`.
- Ограничение попыток — на своей стороне (счётчик + задержка), т.к. сервер, похоже,
  не ограничивает (проверено слабо, см. §8).

### 6.4. WebView (варианты B/C), если понадобится

```kotlin
webView.settings.apply {
    javaScriptEnabled = true
    domStorageEnabled = true          // без этого localStorage пуст
    databaseEnabled = true
    allowFileAccess = false
    allowContentAccess = false
}

webView.webViewClient = object : WebViewClient() {
    // SPA меняет URL через pushState — onPageFinished тут не поможет
    override fun doUpdateVisitedHistory(view: WebView, url: String, isReload: Boolean) {
        if (!url.startsWith(baseUrl)) return
        view.evaluateJavascript(
            "window.localStorage.getItem('impulsecrm_session')"
        ) { raw ->
            val sid = raw?.trim('"')
            if (!sid.isNullOrBlank() && sid != "null" && sid.length > 10) onSession(sid)
        }
    }
}
webView.loadUrl("$baseUrl/login")
```

Обязательно: `WebView` только с этим origin (проверять `url.startsWith(baseUrl)` в
`shouldOverrideUrlLoading`), без `addJavascriptInterface`, `setAllowFileAccess(false)`,
`setSavePassword(false)`, `WebViewAssetLoader` не нужен. После получения сессии —
`webView.destroy()`.

### 6.5. Безопасность

- HTTPS + certificate pinning (осторожно с ротацией Let's Encrypt: пиннить промежуточный
  CA либо использовать `network_security_config` с backup-пином).
- Не логировать тела запросов на логине; в Crashlytics — редактировать.
- Play Integrity API — чтобы BFF (вариант D) принимал запросы только от вашего
  подписанного приложения.
- Сессия в query-параметре попадает в логи nginx. Проверьте, принимает ли сервер
  `Cookie: PHPSESSID=…` — если да, используйте cookie (заголовок), а не query.

### 6.6. Тесты

- `MockWebServer`: успех (`{"success":true,"session":"..."}`), `403` с `message`,
  `200` с `success:false`, пустое тело, таймаут.
- Интеграционный тест «логин → `user/current` → список клиентов» на тестовом стенде.
- UI-тест: истёкшая сессия → редирект на логин.

## 7. Риски

| Риск | Варианты | Что делать |
|---|---|---|
| Вендор закроет/изменит `user/login` | A, D, F | держать C как фолбэк; запросить официальную поддержку (G) |
| Капча/2FA/лимит попыток | A | переход на C/D без изменения остального кода |
| Утечка ключа клиента | A, B, F (если ключ в apk) | не класть ключ в apk; только D/E |
| Утечка сессии (query в логах) | A, C | cookie вместо query, короткий TTL, `logout_devices` |
| Блокировка учётки брутфорсом | все | ограничение попыток на клиенте/BFF |
| Претензии вендора/ToS | A, D, F | письменное согласие; лучше G |
| 152-ФЗ, персональные данные сотрудников | D | минимизация, шифрование, сроки хранения, политика |

## 8. Что нужно проверить живьём (нужны доступы)

Быстрый способ пройти весь чек-лист, **не показывая пароль**: запустить локально
[`check-auth.ps1`](check-auth.ps1). Скрипт спрашивает пароль в консоли (или берёт из
переменной окружения `CHECK_AUTH_PASSWORD`), логинится, прогоняет проверки ниже и пишет
`check-report.json`, в котором нет пароля, а сессия замаскирована — файл можно присылать
как есть.

```powershell
# 1) только логин и работа сессии
powershell -File .\check-auth.ps1 -BaseUrl https://<tenant>.impulsemini.ru -Username +7...

# 2) плюс проверка user/load ключом API (отдаёт ли password/apiToken)
$env:CHECK_AUTH_API_KEY = '<ключ>'
powershell -File .\check-auth.ps1 -BaseUrl https://<tenant>.impulsemini.ru -Username +7...
```

Что смотреть в отчёте: `login.responseKeys` и `login.hasSession` (п. 1),
`session.currentViaQuery.httpStatus` (п. 2), `session.currentViaCookie.httpStatus` (п. 3),
`apiKey.hasPasswordField` / `hasApiTokenField` (п. 4), `session.refreshToken` (п. 5).

Остальное, что нельзя проверить скриптом, — вручную:

1. **Успешный логин** — точный JSON ответа (`session`, есть ли `user`, `role`, `token`),
   ставит ли сервер `Set-Cookie: PHPSESSID`.
2. **Работает ли `?PHPSESSID=<session>` с документированными методами** (`branch/load/1`,
   `client/list`) и с какими правами (права пользователя или ключа).
3. **Принимает ли сервер `Cookie: PHPSESSID=`** (предпочтительнее query).
4. **`user/load/{id}` с ключом клиента** — отдаёт ли `apiToken` и `password` (от этого
   зависит вариант E), и можно ли фильтровать `user/list` по `username`/телефону.
5. **TTL сессии и `user/refresh_token`** — сколько живёт без активности, продлевает ли
   refresh.
6. **Лимит попыток/капча** — аккуратно, на тестовой учётке: 10–15 неверных паролей.
7. **Поведение при смене пароля** в вебе — рвётся ли сессия (важно для UX).

Для этого нужны: телефон и пароль **тестового** сотрудника (не администратора, лучше
специально созданного), а для п. 4 — домен и API-ключ контура. Ключ и пароль присылайте
в личном канале, а не в переписке; после проверки тестовую учётку лучше удалить/сменить
пароль.
