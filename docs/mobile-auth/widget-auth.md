# Авторизация через виджет `/widget/2` (личный кабинет клиента)

Дата: 2026-11-19. Контур: `https://4621c03198bd6735334088.impulsemini.ru`.
Часть передаточного пакета: [README.md](README.md) · архитектура: [architecture.md](architecture.md).
Связанные документы: [android-auth.md](android-auth.md) — авторизация сотрудника (`/login`),
[check-auth.ps1](check-auth.ps1), [widget-probe.ps1](widget-probe.ps1) — воспроизведение
протокола виджета.

> **TL;DR.** `/widget/2` — это личный кабинет **клиента** клуба, а не сотрудника.
> Авторизация устроена так: по номеру телефона виджет получает объект клиента с полем
> `secret` (64 hex-символа) и дальше все запросы подписывает парой `client_id + secret`.
> Пароль проверяется отдельным вызовом `check_password`, но **`secret` выдаётся по одному
> телефону, без пароля**, а вместе с ним — bcrypt-хеш пароля клиента. То есть «вход по
> паролю» здесь декоративный: реальный ключ доступа раздаётся всем, кто знает номер.

## 1. Что такое `/widget/2`

`GET /api/public/widget/load/2` (без авторизации) возвращает конфигурацию виджета:

```json
{"type":2, "id":2, "entity":"widget", "name":"Личный кабинет клиента D'arky Dance",
 "options":{"showBarcode":true,"freezeEnable":true,"paymentWidgetId":1, ...},
 "branches":null, "created":1772184021}
```

`type: 2` — личный кабинет клиента (ЛК): абонементы, посещения, депозиты, заморозка,
запись, штрихкод, оплата. Виджет монтируется SPA-приложением: при `pathname`,
содержащем `/widget/`, фронтенд поднимает отдельный корневой компонент, который по `type`
подгружает нужный модуль (`clientLk/Main.vue` для type 2).

Клиентские учётные данные из задачи относятся именно к
клиенту: staff-логин `POST /api/public/user/login` на них отвечает
`403 {"message":"Пользователь не найден."}`, а виджет их принимает.

## 2. Протокол виджета (проверено на живом контуре)

Все запросы — `POST https://<tenant>/api/public/<метод>` с `Content-Type: application/json`.
Тело — **дважды закодированный JSON**: снаружи JSON-строка, внутри — объект, т.е.
`"{\"phone\":\"...\"}"`. Ответы методов авторизации — обфусцированная строка (см. §4),
ответы методов данных — обычный JSON.

| Шаг | Запрос | Ответ (после декодирования) |
|---|---|---|
| 0 | `GET widget/load/2` | конфиг виджета, без авторизации |
| 1 | `POST widget_schedule/phone_info` `{"phone":"<enc>"}` | `{"count":1,"ids":[255],"hasPassword":1}` |
| 2 | `POST widget_schedule/check_password` `{"phone":"<enc>","password":"..."}` | `{"success":true}` / `{"success":false}` |
| 3 | `POST widget_client_lk/search` `{"phone":"<enc>","socialPage":null}` | профиль клиента: `id`, ФИО, `branch`, **`secret`**, **`settings.password`** (bcrypt) |
| 4 | `POST widget_client_lk/accounts` `{"filters":{"client_id":255,"secret":"<64 hex>"}}` | `{"total":1,"items":[{"trainings":24,"trainingsUsed":4,...}]}` |
| 5 | `POST widget_client_lk/visits` тем же телом | `{"total":89,"items":[...]}` |

Проверено:

- шаг 2 с верным паролем → `{"success":true}`, с неверным → `{"success":false}`;
- шаг 3 выполняется **без пароля** и возвращает `secret` длиной 64 символа;
- шаг 4 с верным `secret` → данные клиента; с неверным `secret` → `LogicException`
  (доступ закрыт), без `secret` → тоже ошибка. Значит, `secret` действительно является
  credential-ом;
- для незнакомого телефона `search` возвращает демо-клиента с `id: -1` — то есть по
  ответу можно проверять, есть ли такой клиент в базе.

Клиент id 255 — тестовый; его данные я не привожу (ФИО, абонементы, 89 посещений
доступны по описанной схеме).

## 3. Кодирование телефона

В бандле (`$string.phoneEncode`):

```js
phoneEncode(phone) {
  const n = Number(phone.replace(/\D/g, '')) + 49680531;
  return base64(reverse(n.toString(36)));
}
```

Никакого ключа: константа `49680531`, base36, переворот строки, base64.
Обратная операция тривиальна. Пример: `+7XXXXXXXXXX` → `<base64>`, см.
`samples/phone-encode.md`.

## 4. Обфускация ответов

`$string.decrypt` из бандла:

```js
xorKey   = reverse('4Lp9Qm2K7x');            // 'x7K2mQ9pL4'
splitSrc = reverse('pQDkZ2ZK0gZkdGZmdmCNYGZnR2n');
sep      = splitSrc.slice(1) + splitSrc[0];   // разделитель — вращённая строка

decrypt(t):
  x = xor(reverse(t), xorKey)
  parts = x.split(sep)
  return base64decode(reverse(parts[0] + parts[1]))
```

Ключи лежат в открытом виде в JS-бандле, схема обратима за пять минут (реализация на
PowerShell — в [widget-probe.ps1](widget-probe.ps1)). Это **кодирование, а не шифрование**:
оно не защищает данные, а только усложняет отладку в браузере.

## 5. Найденные проблемы безопасности

1. **`secret` выдаётся по одному номеру телефона.** `widget_client_lk/search` не требует
   ни пароля, ни сессии: достаточно знать телефон — и вы получаете `client_id` и `secret`,
   которыми подписываются все запросы ЛК (абонементы, посещения, депозиты, заморозка,
   персональные данные). Пароль в этой схеме ничего не защищает.
2. **Утечка хеша пароля.** Тот же ответ содержит `settings.password` — bcrypt-хеш
   (`$2y$10$...`). Он позволяет офлайн-подбор пароля и подтверждает, что пароли хранятся
   стандартным PHP `password_hash`.
3. **Утечка персональных данных.** `search` отдаёт ФИО, филиал, фото, флаги клиента —
   без аутентификации, по номеру.
4. **Перечислимость клиентов.** `phone_info` возвращает `count` и `ids` для любого номера,
   а `search` — профиль; для незнакомого номера создаётся демо-клиент (`id: -1`).
5. **Отладочные ошибки наружу.** Ошибки API отдают стек, полные пути сервера и имена
   классов (`/var/www/.../api/src/Controller/Widget/WidgetClientLkController.php`), что
   упрощает атаку.
6. **Открытый CORS** (см. [android-auth.md](android-auth.md#1-что-проверено-на-живом-контуре)):
   запросы можно делать с любого сайта.

Пункты 1–3 — это фактически обход аутентификации (IDOR + выдача токена по публичному
идентификатору). Рекомендую сообщить вендору impulseCRM; для своего приложения это
означает: **нельзя строить защиту на `secret`** — он не является секретом.

## 6. Варианты авторизации в Android-приложении

### Вариант W1. WebView с самим виджетом (рекомендуется для клиентского приложения)

Приложение открывает `https://<tenant>/widget/2` в `WebView` (или Chrome Custom Tabs),
клиент входит по телефону и паролю, дальше либо весь ЛК живёт в WebView, либо после входа
вы забираете `client_id`/`secret` из состояния приложения и переходите на нативные вызовы.

**Плюсы:** ноль работы по reverse-engineering; вендор сам обновляет UI и чинит дыры;
все функции ЛК доступны сразу; пароль не проходит через ваш код.

**Минусы:** UX, «сайт в рамке», зависимость от мобильной вёрстки виджета; если забирать
`secret` — вы всё равно храните credential, который можно получить по телефону.

**Как забрать состояние:** в `localStorage` виджета лежат `impulsecrm_active` и
`impulsecrm_verified` (base64 от JSON с телефоном), а объект клиента с `secret` — в
состоянии Vue. Надёжнее не вытаскивать, а оставить всё в WebView; если нужно — проще
вызвать `widget_client_lk/search` самому (см. W2).

### Вариант W2. Нативная реализация протокола виджета

Повторяем шаги 1–5 в приложении: `phone_info` → `check_password` → `search` (получаем
`client_id` + `secret`) → запросы ЛК с `filters: {client_id, secret}`.

**Плюсы:** полностью нативный UX, push, офлайн-кеш, контроль над экранами; ответы методов
данных — обычный JSON, дешифровать нужно только ответы авторизации.

**Минусы:**

- обфускация и двойное JSON-кодирование — недокументированный контракт, ломается при
  обновлении продукта;
- `secret` в приложении = постоянный доступ к ЛК, при этом **его может получить любой,
  кто знает телефон** — то есть защита иллюзорна;
- хеш пароля и ПДн ходят по сети (пусть и под obfuscation);
- нет нормального TTL/refresh: `secret`, судя по всему, статичен.

### Вариант W3. BFF: свой сервер между приложением и виджетом (рекомендуется, если нужен нативный UX)

Приложение → ваш API (HTTPS, Play Integrity) → виджет-API.

1. Приложение отправляет телефон и пароль (или SMS-код) на ваш сервер.
2. Сервер вызывает `check_password`; при успехе берёт `secret` и хранит его у себя
   (Redis, TTL), приложению выдаёт свой короткоживущий JWT.
3. Все запросы ЛК идут через сервер, который подставляет `client_id`/`secret`.

**Плюсы:** пароль и `secret` не попадают на устройство; можно добавить SMS-код, лимит
попыток, аудит, скрыть хеши и ПДн, кэшировать; при смене контракта виджета правится только
сервер.

**Минусы:** нужен бэкенд; данные клиента проходят через вас (152-ФЗ, ответственность);
юридические отношения с вендором.

### Вариант W4. Вход по SMS-коду

В виджете уже есть `widget_schedule/flashcall` и `widget_schedule/flashsms` (и
`phone_verify`-экраны), то есть подтверждение номера кодом реализовано вендором. Для
мобильного приложения это привычнее пароля и не требует хранить пароль.

**Плюсы:** нет пароля на устройстве, привычный UX, номер подтверждён.

**Минусы:** нужен шлюз (у вендора уже есть); сам по себе код не решает проблему `secret` —
выдачу токена всё равно надо делать на своём сервере (W3).

### Вариант W5. Официальный мобильный контур

В системе есть `widget_client_mobile/*` (`summary`, `schedule`, `search`, `push_token`,
`notifications`, …) и признак `isMobileApp` в компонентах виджета — то есть у вендора
предусмотрен режим «виджет внутри мобильного приложения». Стоит запросить у вендора
документацию/токен для этого контура: тогда приложение будет работать по поддерживаемому
API, а не по внутреннему протоколу ЛК.

## 7. Сравнение

| Критерий | W1 WebView | W2 нативно | W3 BFF | W4 SMS | W5 вендор |
|---|---|---|---|---|---|
| Скорость | часы | дни | дни | дни | зависит от вендора |
| UX | ★☆☆ | ★★★ | ★★★ | ★★★ | ★★★ |
| Пароль/`secret` не на устройстве | ✓ (если всё в WebView) | ✗ | ✓ | ✓ | ✓ |
| Устойчивость к изменениям API | ✓ | ✗ | ✓ | ✓ | ✓ |
| Закрывает дыру с `search` | — | ✗ | ✓ | ✓ | ✓ |
| Юридические риски | низкие | средние | средние | средние | низкие |

## 8. Рекомендация

1. **Если приложение для клиентов клуба:** начните с **W1** (WebView с `/widget/2`) — это
   самый быстрый и самый устойчивый путь; при потребности в нативном UX — **W3** (BFF),
   тогда `secret` и хеши не попадают на устройство.
2. **W2** — только для прототипа/демо: контракт недокументирован, а модель авторизации
   небезопасна по вине сервера, не по вине приложения.
3. Параллельно — письмо вендору (W5) и уведомление о проблемах из §5: выдача `secret` по
   телефону и возврат хеша пароля — это то, что чинится на их стороне и снимает половину
   рисков вашего приложения.
4. Если приложение — для **сотрудников**, виджет не подходит: там другой контур
   ([android-auth.md](android-auth.md), `POST /api/public/user/login` + `?PHPSESSID=`).

## 9. Что осталось проверить

1. Payload методов `widget_client_mobile/*` (нужен для «официального» мобильного контура) —
   сейчас они отвечают ошибкой на `{filters:{client_id,secret}}`, формат другой.
2. Меняется ли `secret` при смене пароля и есть ли у него срок жизни.
3. Есть ли лимит попыток на `check_password` (проверять аккуратно, на тестовом клиенте).
4. Поведение при нескольких клиентах на один телефон (`ids` — массив).
5. Требуется ли `Referer`/`Origin` для запросов (мои запросы шли с `Referer`, без него не
   проверял системно).
6. Как виджет ведёт себя в мобильном приложении (`isMobileApp`) — возможно, есть
   отдельный режим авторизации.

## 10. Воспроизведение

```powershell
# логин, пароль и проверки — в одном скрипте
powershell -File .\widget-probe.ps1 -Phone '+7XXXXXXXXXX' -Password '<пароль>'
```

Скрипт печатает: закодированный телефон, ответ `phone_info`, ответ `check_password` — то
есть полностью повторяет шаги 1–2. Дальнейшие шаги (search/accounts/visits) выполняются
теми же функциями `PostWidget`/`Decrypt` из скрипта.

## 11. Что доступно с `client_id` + `secret` (и что — нет)

Проверено 2026-11-19 на клиенте id 255 (виджет 2). Скрипт: [widget-surface.ps1](widget-surface.ps1).

### 11.1. Задокументированный API — ничего

Ни один эндпойнт из справочника (`/api/public/<сущность>/<действие>`, 109 операций) с
`client_id`/`secret` недоступен:

| Проверка | Заголовок | Ответ |
|---|---|---|
| `GET branch/load/1` | `Authorization: Basic <secret>` | `401 Требуется аутентификация` |
| `GET branch/load/1` | `Authorization: Bearer <secret>` | `401` |
| `POST client/list` | `Authorization: Basic <secret>` | `401` |
| `GET client/load/255` | `Authorization: Basic <secret>` | `401` |
| `GET branch/load/1` | без заголовка | `401` |

Документированный API принимает только `Authorization: Basic <API_KEY>`. Клиентские
`client_id`/`secret` к нему неприменимы — это разные контуры с разными охранниками.

### 11.2. Недокументированный виджет-API — открыт

Всё, что ниже, вызывается с `{filters:{client_id, secret}}` (или `{client_id, secret}`)
без всякого API key. Ответы — обычный JSON (обфусцированы только ответы авторизации).

**Проверено, отдаёт данные (HTTP 200):**

| Метод | Ответ | Аналог в задокументированном API |
|---|---|---|
| `widget_client_lk/client_summary` | `{"hasBonusItem":true}` | — |
| `widget_client_lk/accounts` | `total=1`, абонемент: 24 занятия, 4 использовано | `group_account/individual_account/self_account/rent_account` → `list` |
| `widget_client_lk/account_detail` | требует доп. параметров | те же → `load` |
| `widget_client_lk/visits` | `total=89`, история посещений | `visit` → `list` |
| `widget_client_lk/deposits` | `total=18`, операции по депозиту | `deposit` → `list` |
| `widget_client_lk/bonuses` | `total=3` | — |
| `widget_client_lk/debts` | `[]` | — |
| `widget_client_lk/reservations` | `total=0` | `reservation` → `list` |
| `widget_client_lk/barcode` | PNG в base64 (штрихкод клиента) | — |
| `widget_client_lk/all_levels` | `total=3` | — |
| `widget_client_lk/product_sections` | `total=0` | `product` (разделы) |
| `widget_client_lk/news` | `[]` (нужен `branches:[id]`) | — |
| `widget_client_lk/stories` | `{"items":[],"viewedStoriesIds":[]}` | — |
| `widget_client_mobile/summary` | расписание, брони, счётчик уведомлений | `schedule` → `list` |

**Авторизация проходит, но нужны другие параметры (HTTP 500 с ошибкой про параметры, не про доступ):**
`widget_client_lk/branch`, `template`, `product_types`, `account_detail`,
`widget_schedule/reservations`, `waitings`, `changes`, `list`.

**Закрыто (401) — это админские методы, клиентские креды не подходят:**
`widget/list`, `widget_pbx/history`, `widget_chat/iframe_url`, `widget/create`,
`widget/oauth_token` и прочие `widget_*` без префикса `client_`.

**Запись (по коду фронтенда; я не выполнял, чтобы не менять данные):**
`prolong_account`, `buy_account`, `buy_product`, `free_order_buy`, `freeze_mix_account`,
`client_in`, `pay_debt`, `update_settings`, `fill_contacts`, `fill_email`, `fill_foto`,
`validate_deposit`, `validate_bonus`, `widget_schedule/create` (запись на занятие),
`unsubscribe` (отмена), `waiting`/`waiting_delete`, `pay`, `save_password`,
`flashcall`/`flashsms`.

### 11.3. Три следствия

1. **Модель прав — «клиентская».** `secret` даёт доступ ровно к одному клиенту
   (`client_id` другого клиента с этим секретом → ошибка `validateSecret`), но не к API
   сотрудников. Для приложения это значит: либо строить клиентский кабинет на
   виджет-API, либо получать у вендора нормальный контур.
2. **`widget_client_mobile/search` тоже отдаёт профиль по телефону** (HTTP 200, без
   пароля) — мобильный контур наследует ту же дыру.
3. **`widget_rent/rents`** с пустым фильтром отвечает 500 с обрывком SQL
   (`select id from client where deleted is NULL AND '`) — похоже на конкатенацию условий;
   стоит проверить на SQL-инъекцию и сообщить вендору.

### 11.4. Итог

С `client_id` + `secret` без API key доступны **только клиентские методы виджета**
(личный кабинет: абонементы, посещения, депозиты, бонусы, брони, штрихкод, новости,
расписание) — и, из-за выдачи `secret` по телефону, доступны они для **любого** клиента,
чьей номер известен. Задокументированный API (клиенты, расписание, группы, продажи,
сотрудники) остаётся закрытым: для него нужен `Authorization: Basic <API_KEY>`.
## 12. Общее расписание занятий: где оно есть

Короткий ответ: **в `widget_client_lk/*` метода для общего расписания нет.** Метод
`widget_client_lk/schedule` возвращает только занятия самого клиента (у тестового
клиента — 1 запись; параметр `range` он игнорирует). Общее расписание отдают методы
других пространств имён, причём **доступны они вообще без `client_id`/`secret`**.

### 12.1. Методы

| Метод | Что возвращает | Нужны ли креды |
|---|---|---|
| `widget_client_lk/schedule` | занятия клиента (1 запись) | да |
| `widget_schedule/list` | общее расписание филиала на период | **нет** (200 без кредов) |
| `widget_client_mobile/schedule` | то же самое (те же 93 записи) | **нет** |
| `widget_schedule/places` | свободные места `{group, self}` | нет (нужен `branch_id`) |
| `widget_schedule/group_description/{id}` | описание группы (GET) | нет |

Тело запроса для расписания:

```json
{
  "branch_id": 1,
  "range":   { "from": 1795030516, "to": 1796240116 },
  "filters": { "groups": true, "individuals": true, "rents": true, "branch_id": 1 }
}
```

Проверено: 14 дней, филиал 1 → `total: 93`, `itemCounts` по типам:

| `type` | `typeTitle` | Кол-во |
|---|---|---|
| 0 | Группа | 34 |
| 1 | Индивидуальное занятие | 41 |
| 2 | Аренда | 18 |

Поля записи: `group` (с `style` и `teacher1`/`teacher2`), `hall`, `day`, `minutesBegin`,
`minutesEnd`, `regular`, `date`/`dateBegin`, `type`, `typeTitle`, `color`, `note`, `wage`.
Пример: «Творческая группа | Шашкова | 780–840 (13:00–14:00) | day=7 | зал Средний».

### 12.2. Замечание по приватности

В записях аренды (`type: 2`) приходит полноценный объект `client` — ФИО, статус, депозит,
бонусы, LTV/RFM. То есть публичное расписание раскрывает данные **других** клиентов,
арендующих залы. Это стоит добавить в письмо вендору вместе с историей про `search`.

### 12.3. Что это значит для приложения

Если приложению нужно общее расписание (запись на занятие, просмотр сетки) — используйте
`widget_schedule/list` или `widget_client_mobile/schedule`: они не требуют ни API key, ни
клиентских кредов, а параметры те же, что у виджета записи. `widget_client_lk/schedule`
для этого не подходит — он про «мои занятия».
### 12.4. Клиент в записях расписания (проверено)

Отдельного скалярного поля `client_id` в записи расписания **нет**. Вместо него —
вложенный объект `client`, и заполнен он по-разному в зависимости от `type`:

| `type` | Записей | С `client` | Что внутри |
|---|---|---|---|
| 0 «Группа» | 34 | 0 | `client: null` |
| 1 «Индивидуальное занятие» | 41 | 41 | объект клиента |
| 2 «Аренда» | 18 | 18 | объект клиента |

Структура объекта (индивидуальное занятие):

```json
"client": {
  "id": 104, "entity": "client",
  "lastName": "...", "name": "...", "middleName": "...",
  "status": {"id": 8, "name": "...", "pipeline": {...}, "color": "CCF261"},
  "level": null, "user": null,
  "deposit": 1800, "bonus": 0,
  "rfm": ..., "ltv": ...,
  "utm": null, "chatType": ..., "pushToken": ...,
  "tag": ..., "age": ...,
  "fotoThumbUrl": "..."
}
```

То есть идентификатор доступен как `item.client.id` (не `item.client_id`), вместе с ФИО,
статусом воронки, депозитом, бонусами, LTV/RFM и фото. Телефона в объекте нет.

**Следствие:** публичное расписание (без кредов) раскрывает не только факт занятия, но и
кто именно записан на индивидуальное занятие и сколько у него денег на депозите. Для
приложения это удобно (можно показать «ваше занятие»), но это ещё одна утечка ПДн,
которую стоит отправить вендору.
