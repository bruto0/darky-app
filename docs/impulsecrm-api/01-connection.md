## Где находится API

`https://tech.impulsecrm.ru/api/` — это **веб-интерфейс документации** (Vue-приложение
со списком сущностей и песочницей «Попробовать запрос»). Сам REST API живёт на домене
конкретной CRM:

```
https://<домен-вашей-crm>/api/public/<сущность>/<действие>
```

Например, для демо-контура: `https://demo.impulsecrm.ru/api/public/client/list`.

Проверено на живом сервере:

- `GET https://demo.impulsecrm.ru/api/public/branch/load/1` без ключа → `401`
  `{"message":"Требуется аутентификация"}` — эндпойнт существует и защищён;
- `POST https://tech.impulsecrm.ru/api/public/client/list` → `404` (HTML-страница ошибки) —
  на домене документации методов API нет.

Поэтому в примерах используется переменная `$IMPULSE_BASE_URL` — подставьте адрес своей
CRM (без завершающего `/`).

## Базовый URL и префикс

| Параметр | Значение |
|---|---|
| Базовый URL | `https://<домен-crm>` (демо: `https://demo.impulsecrm.ru`) |
| Префикс API | `/api/public` |
| Полный путь | `/api/public/{ключ-сущности}/{действие}` |
| Транспорт | HTTPS, HTTP/1.1 |
| Формат тела | JSON (`Content-Type: application/json`), UTF-8 |

Ключи сущностей и действия перечислены в [индексе](03-entities/README.md) и
[02-actions.md](02-actions.md).

## API-ключ

1. Войдите в CRM под пользователем, от имени которого будет работать интеграция.
2. Откройте меню профиля → **«Настройка API»**.
3. Нажмите **«Обновить ключ»** и скопируйте значение.

Ключ привязан к пользователю: права интеграции равны правам этого пользователя. В
сущности [`user`](03-entities/user.md) есть поле `apiToken` — вероятно, там хранится
действующий ключ (проверьте на своём контуре, прежде чем полагаться на это). Кнопка
«Пример запроса» в том же окне показывает рабочий вызов с вашим ключом.

> Ключ — секрет. Храните его в переменной окружения или в секрете CI, не в репозитории и
> не в переписке. Перевыпуск ключа («Обновить ключ») немедленно ломает старые интеграции.

## Авторизация

Ключ передаётся в заголовке `Authorization` по схеме Basic:

```
Authorization: Basic <API_KEY>
```

Ключ подставляется после слова `Basic` **как есть**, без base64. Это проверено на
демо-контуре: `Authorization: Basic d7b6…` → `200`, а варианты
`Basic base64(ключ)` и `Basic base64(ключ:)` → `401`. Стандартное для RFC 7617
кодирование здесь не применяется.

Рабочий вариант фиксируется первым же запросом (см. «Проверка подключения»), после этого
используйте его во всех вызовах.

Заголовки запроса:

| Заголовок | Обязателен | Значение |
|---|---|---|
| `Authorization` | да | `Basic <API_KEY>` |
| `Content-Type` | для POST с телом | `application/json` (кодировка UTF-8) |
| `Accept` | нет | `application/json` |

## Проверка подключения

Самый дешёвый запрос — чтение справочной сущности (филиал с `id=1`); его же использует
кнопка «Проверить» в документации:

```bash
curl -s -g "$IMPULSE_BASE_URL/api/public/branch/load/1" \
  -H "Authorization: Basic $IMPULSE_API_KEY"
```

- `200` и JSON-объект филиала — ключ и адрес верны;
- `401 {"message":"Требуется аутентификация"}` — неверный ключ, заголовок или домен;
- `404` HTML — неверный путь (например, забыт `/public` или используется домен
  документации);
- `500` / HTML-страница ошибки — проблема на стороне CRM, смотрите
  [06-troubleshooting.md](06-troubleshooting.md).

## Форматы данных

API работает с JSON. Типы полей в справочнике: `number`, `string`, `boolean`, `array`,
`object`.

| Что | Как передаётся |
|---|---|
| Дата/время | Unix timestamp в **секундах**, UTC: `1767214800` |
| Время занятия | Минуты от начала суток: `960` = 16:00 |
| Ссылка на другую запись | Объект с одним полем `id`: `{"id": 3}`; в ответах — полноценный объект |
| Идентификаторы | Числа: `id`, `client_id`, `level_id` |
| Телефоны | Массив строк: `["79130000000"]` |
| E-mail, соцсети, адрес | **Массив строк** и при создании, и в ответе: `["a@b.ru"]` (в документации сказано «строка с разделителем» — это неверно) |
| Пустое значение | `null` (в примерах документации часто `null` = «не передавать») |
| Массив идентификаторов при удалении | `[12, 34]` |
| Флаг успеха | `true` / `false` в поле `success` |

Даты в примерах документации — будущие даты (2026–2027), это нормально: они взяты из
тестового контура.

## Форматы ответов

| Действие | Успешный ответ (проверено на демо) |
|---|---|
| `load` (GET) | Объект сущности: `{"id": 1, "entity": "client", ...}` |
| `list` (POST) | `{"total": 97, "items": [ {...}, {...} ]}` |
| `update` без `id` (создание) | `{"success": true, "id": 42, "updated": null}` |
| `update` с `id` | `{"success": true, "id": 42, "updated": 1795021719}` — время изменения |
| `delete` | `{"success": true}` |
| `product` (создание) | `{"success": true, "id": [3], "updated": null, "kkt": null}` — `id` массивом |
| `reservation` (создание) | `{"success": true, "count": 1}` — сколько записей создано |
| `deposit/input`, `deposit/output` | `{"success": true, "id": 690, "kkt": null}` — `id` операции |

HTTP-код при успехе — `200`, но **не только**: бизнес-правила (конфликт занятия, лимит
удаления депозита) возвращают `200` с `{"success": false, "message": "…"}`. Ошибки
валидации и БД — `500` с plain-text и стеком. Поэтому проверяйте `success` и наличие
ожидаемых данных, а не только код.

## Ошибки

| Код | Тело | Причина |
|---|---|---|
| `401` | JSON `{"message":"Требуется аутентификация"}` | нет/неверный заголовок `Authorization`, отозванный ключ |
| `404` | HTML «An Error Occurred: Not Found» | неверный путь или маршрут, которого нет (`/visit/load/1`, `/deposit/load/1`), домен документации вместо домена CRM |
| `405` | Текст `No route found for "GET /client/list": Method Not Allowed (Allow: POST)` | неверный HTTP-метод |
| `500` | **Plain text**: SQL-запрос, имя исключения, стек вызова | невалидные данные, нарушение NOT NULL, бизнес-правила, несуществующий `id` |
| `200` + `{"success": false, "message": "…"}` | JSON | операция не выполнена (конфликт занятия, лимит удаления депозита) |

Важно: `500` — это не JSON, а текст с SQL и внутренними путями сервера (утечка
информации). Не показывайте его пользователям и не логируйте в открытом виде. Загрузка
или удаление несуществующего `id` тоже даёт `500`, а не `404`.

Тексты бизнес-ошибок приходят в `message` — их можно показывать пользователю (например,
«В указанное время уже есть занятие: …»).

## Ограничения и особенности

- **Лимит частоты:** жёсткого ограничения нет, рекомендуется **не более 10 запросов в
  секунду**.
- **Пагинация:** по умолчанию `list` может вернуть все записи; для больших выборок
  обязательно используйте `limit` + `page` (см. [02-actions.md](02-actions.md#list)).
- **CORS:** сервер отдаёт `Access-Control-Allow-Origin: *`, поэтому вызовы из браузера
  технически возможны, но ключ в браузерном коде раскрывается — используйте серверную
  интеграцию.
- **Идемпотентности нет:** повторный `update` без `id` создаст дубль. Для защиты от
  дублей ищите запись через `list`/`filters` перед созданием.
- **Массовые операции:** пакетно удалять можно (`delete` принимает массив `id`), пакетного
  создания/обновления нет — только последовательные вызовы.
