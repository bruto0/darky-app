# 06. Диагностика типовых проблем

[← Сценарии](04-scenarios.md) · [Оглавление](README.md)

## 401 «Требуется аутентификация»

Тело: `{"message":"Требуется аутентификация"}`.

Проверьте по порядку:

1. **Домен.** Запрос идёт на домен вашей CRM, а не на `tech.impulsecrm.ru` (там API нет).
   Путь должен начинаться с `/api/public/`.
2. **Заголовок.** `Authorization: Basic <API_KEY>` — целиком, без кавычек вокруг ключа,
   без пробелов внутри.
3. **Вариант кодирования.** Если экземпляр не принимает ключ «как есть», используйте
   base64 от `ключ:`:
   `Authorization: Basic $(printf '%s' "$IMPULSE_API_KEY:" | base64)`.
4. **Ключ актуален.** Перевыпуск ключа в профиле («Обновить ключ») отзывает старый.
5. **Пользователь активен и имеет права** на эту сущность (ключ наследует права
   пользователя).

Быстрая проверка:

```bash
curl -s -i "$IMPULSE_BASE_URL/api/public/branch/load/1" \
  -H "Authorization: Basic $IMPULSE_API_KEY" | head -20
```

`200` — всё в порядке; `401` — проблема в ключе/заголовке; `404` — проблема в пути/домене.

## 404 «An Error Occurred: Not Found» (HTML)

HTML-страница ошибки вместо JSON означает, что запрос не дошёл до API:

| Причина | Как исправить |
|---|---|
| Используется `https://tech.impulsecrm.ru` | Заменить на домен своей CRM |
| Пропущен `/public`: `/api/client/load/1` | `/api/public/client/load/1` |
| Опечатка в ключе сущности: `clients`, `group-account` | Только точные ключи из [индекса](03-entities/README.md): `client`, `group_account` |
| Неверное действие: `get`, `read`, `load/1/` | `load` (GET), `list`, `update`, `delete` (POST) |
| Лишний `/` в конце пути | Убрать завершающий слэш |

## Ответ 200, но операция не выполнена

API может вернуть `200` с `{"success": false, ...}`. Всегда проверяйте тело:

```bash
curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/delete" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" -d '[999999]'
```

Если запись не существует, `success` будет `false` (или вернётся `404`) — это не сбой
транспорта.

## `list` возвращает пустой `items`

1. **Фильтр слишком строгий.** Уберите `filters`/`columns` и повторите запрос — так видно,
   есть ли данные вообще.
2. **Неверный тип значения.** Даты — секунды (`1767214800`), не миллисекунды и не строки
   `2026-01-01`; числа — числа, не строки.
3. **Связь фильтруется не тем ключом.** Для связи пробуйте `{"status": {"id": 3}}`; вариант
   `{"status": {"number": 2}}` зависит от структуры связанной сущности.
4. **`columns` отсекает всё.** `columns` проверяет уже выбранные записи, `{"ltv": ">500"}`
   отбросит всё, где `ltv` пустой.
5. **Записи удалены.** Логически удалённые (`deleted: true`) в выборку не попадают.
6. **`page` за пределами.** Если `page` больше числа страниц, `items` пуст, а `total > 0`.

## Фильтры не применяются

Проверено на демо — половина документированных конструкций не работает. Используйте
рабочий минимум:

- `filters` — объект, а не массив: `{"deposit": 0}`, не `[{"deposit": 0}]`.
- Строка в `filters` — это **LIKE**: `{"lastName": "Петров"}`. Для строгого сравнения —
  `columns` с `{"equal": ...}` (только для строк).
- `{"поле": null}` — «поле NULL» (работает), а `"empty"` — **не** работает: не совпадает
  ни с NULL, ни с FALSE.
- `{"not": ...}` возвращает `500` (SQL-ошибка) — «не равно» проверяйте на своей стороне.
- Для связей `{"status_id": 1}` / `{"status": {"id": 1}}` работают, а документированный
  `{"status": {"number": 1}}` — нет (0 записей).
- Неизвестное поле в `filters` игнорируется (вернутся все записи), в `columns` — `500`.
- Числовой диапазон `{"age": {"from": 18}}` игнорируется; `from`/`to` работают для дат.
- У `deposit` фильтр `client_id` обязателен — иначе выборка по всем клиентам.

## 500 и текст ошибки

`500` — это не JSON, а plain text с SQL-запросом, именем исключения и стеком. Частые
причины:

- не переданы обязательные поля, в том числе «технические» (`deposit`, `bonus`, `options`,
  `wageOptions`, `status`, `number`, `payBox`, `shift`, `pays`);
- неверный тип: строка вместо массива (`email`, `socialPage`, `address` у клиента), число
  вместо строки и наоборот;
- `list` с пустым телом `{}` → «Укажите параметры запроса.»;
- `deposit/delete` с более чем одной операцией → «Можно удалить только 1 операцию.»;
- несуществующий `id` при `load`/`update`/`delete` (вместо ожидаемого `404`);
- несуществующий `id` связи в теле (`branch`, `style`, `teacher`, `hall`, `payBox`,
  `shift`, `client`).

Сохраните тело запроса и первые строки ответа: в тексте ошибки обычно прямо указано поле
(например, «Column 'options' cannot be null»).

## Создались дубли

`update` без `id` всегда создаёт новую запись — идемпотентности нет. Перед созданием
ищите существующую запись:

```bash
curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/list" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"fields": ["id"], "filters": {"phone": "79130000000"}, "limit": 1}'
```

## Массовое удаление удалило не всё

`delete` возвращает общий `success`; если часть `id` не существует или недоступна, часть
записей может остаться. После операции проверьте `list` по тем же `id`:

```bash
curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/list" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"fields": ["id"], "filters": {"id": [123, 124, 125]}}'
```

## Запросы стали медленными или сервер отвечает ошибкой

- Всегда указывайте `limit` (100–500) и `fields` — «все поля всех записей» дорого.
- Не запрашивайте `list` без `limit` на таблицах `client`, `visit`, `deposit`, `product`.
- Соблюдайте ~10 запросов в секунду; при массовой обработке добавьте паузу
  (`sleep 0.1` между вызовами).
- Для больших выгрузок сортируйте по `id` и идите страницами.

## CORS и вызовы из браузера

Сервер отдаёт `Access-Control-Allow-Origin: *`, поэтому запросы из браузерной страницы
технически проходят. Но ключ в браузерном коде видят все пользователи и расширения —
для продакшена вызывайте API со своего сервера или через прокси. Если браузер блокирует
`Authorization` в preflight-запросе, добавьте прокси, который подставляет заголовок на
стороне сервера.

## Особенности исходной документации

Полный список расхождений, проверенных на живом API, — в
[07-verification.md](07-verification.md#diffs).
Коротко:

1. **Путь `load` у части сущностей** в документации показан сокращённо — `/api/client/1`.
   Рабочий путь у всех: `/api/public/{entity}/load/{id}`.
2. **`deposit/output`**: `sum` описан как `string` (`"100"`), у `deposit/input` — `number`.
   Передавайте число; если списание не проходит, проверьте оба варианта.
3. **`deposit/delete`**: в описании тела написано «Идентификатор зала» — копипаста;
   фактически передаётся `id` операции депозита, и только один за вызов.
4. **`group.placeCount`**: тип `number`, пример — строка `"10"`. Передавайте число.
5. **`informer`/`pipeline`**: в документации только `list`, но `load`/`update`/`delete`
   тоже работают.
6. **`list` без параметров** в документации разрешён, фактически — `500`.
7. **`visit/list`**: в тексте «ответ — JSON-массив», в схеме — `{total, items}`.
   Фактически приходит `{total, items}`.
8. **Ошибки валидации** не описаны: это `500` с текстом и стеком (см. выше).

## Песочница в документации

На странице <https://tech.impulsecrm.ru/api/> есть блок «Попробовать запрос»: укажите URL
своей CRM, ключ, выберите метод — и страница отправит запрос через свой прокси и покажет
ответ. Это удобно, чтобы проверить ключ и увидеть реальную структуру ответа, не подставляя
ключ в браузерный код своего приложения.
