# 02. Действия API: чтение, создание, изменение, удаление, выборки

[← Подключение](01-connection.md) · [Оглавление](README.md) · [Сценарии →](04-scenarios.md)

## Общая схема

```
POST/GET  {BASE}/api/public/{entity}/{action}
```

- `{entity}` — ключ сущности: `client`, `group`, `group_account`, `schedule`, …
  ([индекс](03-entities/README.md));
- `{action}` — одно из действий ниже;
- авторизация — заголовок `Authorization: Basic <API_KEY>` во всех запросах.

| Операция | Действие | Метод | Путь | Тело |
|---|---|---|---|---|
| Получить одну запись | `load` | `GET` | `/api/public/{entity}/load/{id}` | нет |
| Получить набор | `list` | `POST` | `/api/public/{entity}/list` | объект выборки |
| Создать | `update` (без `id`) | `POST` | `/api/public/{entity}/update` | объект сущности |
| Изменить | `update` (с `id`) | `POST` | `/api/public/{entity}/update` | объект сущности + `id` |
| Удалить | `delete` | `POST` | `/api/public/{entity}/delete` | массив `id` (у `schedule` — объект) |

Не у всех сущностей есть все действия:

| Сущность | Особенность |
|---|---|
| `informer`, `pipeline` | только `list` — справочники, доступны только на чтение |
| `visit` | только `list` и `delete` — посещения создаются автоматически при списании абонемента |
| `deposit` | `list`, `delete` + специальные `input` (пополнение) и `output` (списание) |
| `schedule` | `delete` принимает не массив, а объект `{"item": {"id": …}, "date": …}` |
| `reservation` | создание возвращает `{"success": true, "count": N}` |

## Действие load — получить запись по идентификатору

```
GET /api/public/{entity}/load/{id}
```

Тело не передаётся, `id` — в пути. Ответ — объект сущности целиком.

```bash
curl -s -g "$IMPULSE_BASE_URL/api/public/client/load/1" \
  -H "Authorization: Basic $IMPULSE_API_KEY"
```

> В документации пример пути для `load` иногда показан сокращённо (`/api/client/1`).
> Рабочий и единый для всех сущностей вид — `/api/public/{entity}/load/{id}`; он же
> указан в поле `pathTemplate` исходного JSON.

Если запись не найдена, API возвращает `404` или `200` с `success: false` — проверяйте
тело ответа, а не только код.

## Действие update — создание и изменение

Один и тот же URL выполняет две операции:

| Что нужно | Тело запроса | Результат |
|---|---|---|
| Создать запись | объект сущности **без** `id` (или `"id": null`) | новая запись, в ответе её `id` |
| Изменить запись | тот же объект **с** `id` существующей записи | обновлённая запись, в ответе тот же `id` |

```bash
# Создание клиента (id не передаём)
curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/update" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"entity": "client", "name": "Иван", "lastName": "Петров", "phone": ["79130000000"]}'

# Изменение того же клиента (передаём id)
curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/update" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"id": 42, "entity": "client", "name": "Иван", "lastName": "Петров", "phone": ["79130000000"], "email": "ivan@example.com"}'
```

Правила:

- **Обязательные поля** указаны в таблице тела запроса на странице сущности (колонка
  «Обязательное»). Без них запрос вернёт ошибку. На практике демо-контура обязательных
  полей больше, чем в документации (см. [07-verification.md](07-verification.md#minimal)).
- Поле `entity` есть у большинства сущностей (`"client"`, `"groupAccount"`, …). Значение
  для каждой сущности написано в шапке её страницы.
- Связанные записи передаются объектом только с `id`: `{"id": 3}` — клиент, группа,
  преподаватель, зал, касса, смена и т.п.
- Ответ: `{"success": true, "id": <id записи>, "updated": null}`. У `reservation` —
  `{"success": true, "count": N}`, у `product` — `id` **массивом** (`"id": [3]`).
- **Обновление частичное:** достаточно передать `id` и изменяемые поля, остальные
  сохраняются (проверено: `lastName`, `phone`, `email` не сбрасываются). Полный объект
  передавать не обязательно.
- Контактные поля клиента (`email`, `socialPage`, `address`) — массивы строк, не строки.
- Идемпотентности нет: повторный вызов без `id` создаст вторую запись.

## Действие delete — удалить записи

```
POST /api/public/{entity}/delete
```

Тело — **JSON-массив идентификаторов**, одной операцией можно удалить одну или несколько
записей:

```bash
# Один клиент
curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/delete" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '[42]'

# Несколько клиентов сразу (группа записей)
curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/delete" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '[42, 43, 44]'
```

Ответ: `{"success": true}`.

Особые случаи (проверено на демо):

| Сущность | Тело и поведение |
|---|---|
| `schedule` | объект: `{"item": {"id": 119, "entity": "schedule"}, "date": 1775174400}` — удаляется занятие на дату; при наличии записей вернётся `success: false` с текстом |
| `deposit` | массив из **одной** операции: две и более → `500 «Можно удалить только 1 операцию.»`; удаление операции откатывает баланс |
| `visit` | массив `id` посещений |

Удаление **логическое**: запись получает `deleted: true`, остаётся доступной через `load`,
но исчезает из `list`. Повторное удаление возвращает `{"success": true}`. Восстановить
запись через API нельзя, поэтому удаляйте только после проверки `load`/`list`.

## Действие list — выборка записей

```
POST /api/public/{entity}/list
Content-Type: application/json
```

Тело — объект с параметрами. **Хотя бы один параметр обязателен:** пустой `{}` возвращает
`500 «Укажите параметры запроса.»` (проверено на демо).

| Параметр | Тип | Назначение | Пример |
|---|---|---|---|
| `fields` | `array<string>` | какие поля вернуть у каждой записи; без него — все поля | `["id", "name", "phone"]` |
| `limit` | `number` | размер страницы; без него — все подходящие записи | `10` |
| `page` | `number` | номер страницы, начиная с `1`; работает только вместе с `limit` | `1` |
| `sort` | `object` | сортировка: `{"поле": "asc" \| "desc"}` | `{"created": "desc"}` |
| `filters` | `object` | фильтрация **на уровне БД** по полям и связям | `{"branch": {"id": 1}}` |
| `columns` | `object` | фильтрация по значениям полей (работает частично, см. ниже) | `{"created": {"from": 1767214800}}` |

Ответ:

```json
{
  "total": 128,
  "items": [
    {"id": 1, "name": "Иван", "phone": ["79130000000"]}
  ]
}
```

`total` — сколько записей подходит под условия **всего** (не на странице). Если `limit` не
указан, `items` содержит всю выборку — на больших таблицах это долго и опасно по памяти,
поэтому всегда ограничивайте `limit`. `total` может быть больше длины `items` (например,
из-за прав пользователя) — не считайте `items` полным списком, если `total` отличается.

### Параметр filters — фильтрация на уровне БД

Ключи — имена полей сущности (или связей), значения — условие. Условия по разным полям
объединяются по «И».

| № | Условие | Формат | Пример | Проверено на демо |
|---|---|---|---|---|
| 1 | Равно | `{"поле": значение}` | `{"deposit": 1000}` | ✅ |
| 2 | По id связанной сущности | `{"поле": {"id": ID}}` | `{"status": {"id": 3}}` | ✅ |
| 3 | Список значений (IN) | `{"поле": [знач1, знач2]}` | `{"id": [1, 2, 3]}` | ✅ |
| 4 | Диапазон дат | `{"поле": {"from": a, "to": b}}` | `{"created": {"from": 1609459200, "to": 1612137599}}` | ✅ |
| 5 | Только «от» или «до» | `{"поле": {"from": a}}` / `{"поле": {"to": b}}` | `{"created": {"from": 1672531200}}` | ✅ для дат |
| 6 | Не равно | `{"поле": {"not": значение}}` | `{"deposit": {"not": 0}}` | ❌ 500 (SQL-ошибка) |
| 7 | Пусто (NULL или FALSE) | `{"поле": "empty"}` | `{"deleted": "empty"}` | ❌ не совпадает с NULL/FALSE |
| 8 | Содержит подстроку (LIKE, без учёта регистра) | `{"поле": "фрагмент"}` | `{"lastName": "Петров"}` | ✅ |
| 9 | Строго NULL | `{"поле": null}` | `{"parent1": null}` | ✅ |
| 10 | По внешнему ключу `*_id` | `{"поле_id": ID}` | `{"status_id": 1}` | ✅ |

Что ещё выяснилось на демо:

- неизвестное поле в `filters` **молча игнорируется** (вернутся все записи) — опечатка в
  имени поля не даст ошибку;
- числовой диапазон `{"age": {"from": 18}}` игнорируется (работает только для дат);
- фильтр из документации `{"status": {"number": 1}}` вернул **0** записей, хотя записи со
  статусом №1 есть; рабочие варианты — `{"status": {"id": 1}}` или `{"status_id": 1}`;
- `{"deleted": false}` вернул все записи (фильтр по `false` игнорируется), `"empty"` — 0.

Пример: клиенты со статусом №1, созданные с 1 января 2023, с ненулевым депозитом
(`not` не поддерживается, поэтому «ненулевой» проверяйте на своей стороне):

```json
{
  "filters": {
    "status_id": 1,
    "created": {"from": 1672531200},
    "deposit": 1000
  }
}
```

### Параметр columns — фильтрация по значениям полей

`columns` — объект «поле → правило». На демо-контуре работает **частично**, поэтому для
отбора используйте `filters`, а `columns` — только для строковых `equal` и числовых
сравнений.

| № | Условие | Формат | Пример | Проверено на демо |
|---|---|---|---|---|
| 1 | Точное совпадение | `{"поле": {"equal": значение}}` | `{"name": {"equal": "Елена"}}` | ✅ для строк; для чисел игнорируется |
| 2 | Интервал дат | `{"поле": {"from": ts, "to": ts}}` | `{"created": {"from": 1609459200, "to": 1612137599}}` | ✅ |
| 3 | Числовое сравнение | `{"поле": "операторчисло"}` — без пробела, операторы `=`, `>`, `<`, `>=`, `<=` | `{"age": ">20"}` | ✅ (кроме `id`: всегда 0) |
| 4 | Содержит подстроку | `{"поле": "фрагмент"}` | `{"address": "Московская"}` | ✅ |

Ограничения, выявленные на демо:

- `columns` без `fields`/`limit` даёт `500`;
- неизвестное поле в `columns` → `500` (в отличие от `filters`, где оно игнорируется);
- сравнения по `id` (`{"id": ">10"}`) всегда возвращают 0 записей;
- `{"age": {"equal": 20}}` игнорируется — для чисел используйте `{"age": "=20"}` или `{"age": ">20"}`.

Пример (клиенты старше 20 лет, имя содержит «Елена»):

```json
{
  "fields": ["id", "name", "age"],
  "columns": {"name": "Елена", "age": ">20"},
  "limit": 10
}
```

`filters` и `columns` можно комбинировать: сначала БД отбирает по `filters`, затем
выборка уточняется по `columns`. Если комбинация возвращает 500, уберите `columns` и
проверьте результат.

### Постраничная выгрузка

```bash
page=1
while :; do
  response=$(curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/list" \
    -H "Authorization: Basic $IMPULSE_API_KEY" \
    -H "Content-Type: application/json" \
    -d "{\"limit\": 100, \"page\": $page, \"sort\": {\"id\": \"asc\"}}")
  echo "$response" | python -c 'import json,sys; d=json.load(sys.stdin); [print(i["id"]) for i in d["items"]]'
  count=$(echo "$response" | python -c 'import json,sys; print(len(json.load(sys.stdin)["items"]))')
  [ "$count" -lt 100 ] && break
  page=$((page+1))
done
```

Правила пагинации:

- `page` считается с `1`;
- сортируйте по стабильному полю (`id`, `created`), иначе между страницами возможны
  пропуски и дубли;
- ориентируйтесь на `total` и на длину `items` (последняя страница короче `limit`).

### Как получить все записи

1. `list` без `limit` — только для небольших справочников (`style`, `hall`, `branch`,
   `informer`, `pipeline`).
2. Для рабочих таблиц (`client`, `visit`, `deposit`, `product`) — пагинация по 100–500
   записей с `sort` по `id`.

## Группы записей (массовые операции)

«Группа сущностей» в API — это либо результат `list` (набор записей), либо массив `id`,
передаваемый в `delete`.

| Задача | Как делать |
|---|---|
| Удалить несколько записей | один `POST …/delete` с массивом `id` |
| Прочитать несколько записей | `list` с `filters: {"id": [1,2,3]}` (IN); если фильтр по `id` не сработает — несколько `load` |
| Изменить несколько записей | цикл `update` по каждой записи (пакетного метода нет) |
| Создать несколько записей | цикл `update` без `id` (пакетного метода нет) |
| Найти записи по условию и удалить | `list` с `filters` → собрать `id` → один `delete` |

Пример «найти и удалить группу»:

```bash
ids=$(curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/list" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"fields": ["id"], "filters": {"blacklist": true}}' \
  | python -c 'import json,sys; print(json.dumps([i["id"] for i in json.load(sys.stdin)["items"]]))')

curl -s -X POST "$IMPULSE_BASE_URL/api/public/client/delete" \
  -H "Authorization: Basic $IMPULSE_API_KEY" \
  -H "Content-Type: application/json" \
  -d "$ids"
```

Массовое изменение — только последовательными вызовами; при десятках записей соблюдайте
лимит ~10 запросов/с и обрабатывайте ответ каждого вызова (частичный успех возможен).

## Соглашения и подводные камни

- **`entity` в теле обязателен** у большинства сущностей и должен совпадать со значением
  из шапки страницы сущности (`client`, `groupAccount`, `rentSingle`, …). Для сущностей
  без поля `entity` (`schedule`, `reservation`, `visit`, `deposit`) оно не передаётся.
- **Вложенные объекты** — только `{"id": N}`. Лишние поля внутри могут игнорироваться, но
  лучше не рисковать.
- **`null` vs отсутствие поля.** В документации `"example": null` означает «не
  передавать». Явный `null` может как очистить поле, так и быть отвергнутым валидацией.
- **Строки с разделителем.** В ответах `email`, `socialPage`, `address`, `pushToken` —
  одна строка с разделителем; при создании `address` у клиента передаётся массивом.
- **Время.** Всё в UTC, секунды. Время занятия — минуты от полуночи (`minutesBegin`,
  `minutesEnd`), день недели — `1` = понедельник.
- **Проверка результата.** Смотрите `success` и `id`/`total`/`items`, а не только
  HTTP-код: часть ошибок приходит с `200`.
