## Расхождения с документацией (фактическое поведение)

1. **`list` требует хотя бы один параметр.** `POST …/list` с телом `{}` возвращает `500`
   «Укажите параметры запроса.»; `{"limit": 1}` уже работает. В документации все
   параметры названы необязательными.
2. **`page` без `limit` не ограничивает выдачу** — возвращаются все записи (97 клиентов).
   Постраничность работает только в паре `limit` + `page`.
3. **`fields` — точная проекция.** Возвращаются ровно запрошенные поля; неизвестное поле
   молча игнорируется; точечные пути (`branch.name`) не поддерживаются — вернётся только `id`.
4. **`sort`** понимает `asc`/`desc`; неверное значение не ошибка — сортировка по возрастанию.
5. **`update` — частичное.** Достаточно передать `id` и изменяемые поля: остальные
   сохраняются (проверено на клиенте: `lastName`, `phone`, `email` не сбросились).
   В документации сказано «передавайте объект целиком» — это не обязательно.
6. **`delete` — логическое удаление.** Запись получает `deleted: true`, остаётся доступной
   через `load`, исчезает из `list`. Повторное удаление возвращает `{"success": true}`.
7. **`deposit/delete` принимает только одну операцию за вызов.** Массив из двух `id` →
   `500 «Можно удалить только 1 операцию.»`. Удаление операции откатывает баланс депозита.
8. **`schedule/delete`** принимает `{"item": {"id": …}, "date": …}`; при наличии записей
   возвращает `{"success": false, "message": "На выбранные занятия уже есть записи…"}`.
   Создание занятия в занятое время — `200` + `success: false` с текстом конфликта.
9. **`filters`:** работают точное совпадение, `IN` (`{"id": [1,2]}`), диапазон дат
   (`{"created": {"from": …, "to": …}}`), `LIKE` по строке, `null`, связь `{"branch": {"id": 1}}`
   и `*_id`. **Не работают:** `{"not": …}` (500, SQL-ошибка), `"empty"` (не совпадает с
   NULL/FALSE, вернул 0 вместо 97), числовой `from` (игнорируется), конструкция из
   документации `{"status": {"number": 1}}` (0 записей — нужен `{"status": {"id": 1}}`
   или `{"status_id": 1}`). Неизвестное поле фильтра игнорируется.
10. **`columns`:** числовые сравнения строкой (`{"age": ">20"}` — работает), `equal` для
    строк (`{"name": {"equal": "Елена"}}` — работает), для чисел `equal` игнорируется,
    сравнения по `id` всегда дают 0, неизвестное поле — 500. Параметр `columns` без
    `fields`/`limit` даёт 500. Используйте `filters` как основной инструмент.
11. **Обязательные поля на демо шире документации:** клиенту нужны `deposit` и `bonus`;
    филиалу и залу — `options`; преподавателю — `wageOptions` и `options`; группе —
    `status` и `*WageOptions`; абонементам — `number`, `payBox`, `shift`, `pays`;
    разовым занятиям — `payBox`, `shift`, `pays`.
12. **Контактные поля клиента — массивы.** `email`, `socialPage`, `address` передаются
    массивами строк (`["a@b"]`), хотя в документации описаны как строка с разделителем.
    Строка в `email` даёт 500 (`setEmail(): Argument #1 must be of type ?array`).
13. **`product` возвращает `id` массивом:** `{"success": true, "id": [3], ...}`. `load`
    работает по элементу массива (`/product/load/3`).
14. **`informer` и `pipeline` поддерживают CRUD** (`load`, `update`, `delete`), хотя в
    документации у них только `list`.
15. **`user`:** создание запрещено правами демо-пользователя —
    `500 «Текущий пользователь не может редактировать пользователей.»`.
16. **`total` может быть больше `items`:** у `user` при `total = 3` вернулось 2 записи —
    похоже на фильтрацию по правам. Не считайте `items` полным списком без проверки.

## Коды и формат ошибок

| Ситуация | Ответ |
|---|---|
| Нет/неверный ключ | `401`, JSON `{"message":"Требуется аутентификация"}` |
| Неизвестный маршрут (`/visit/load/1`, `/deposit/load/1`, `/nosuch/list`) | `404`, HTML-страница Yii |
| Неверный метод (`GET /client/list`) | `405`, текст `No route found for "GET /client/list": Method Not Allowed (Allow: POST)` |
| Ошибка валидации/БД | `500`, **plain text** с SQL, именем исключения и стеком (утечка внутренних путей) |
| Бизнес-правило (конфликт занятия, лимит удаления депозита) | `200` + `{"success": false, "message": "…"}` либо `500` с текстом |
| Пустой `list` | `500` «Укажите параметры запроса.» |
| Удаление/загрузка несуществующего `id` | `500` (TypeError в репозитории) — не `404` |

Вывод для интеграции: **не полагайтесь на HTTP-код** — проверяйте `success` и текст
`message`; логируйте тело ответа, но не показывайте его пользователям (там есть SQL и
пути сервера).

## Рекомендации по работе с API (по итогам проверки)

1. Перед созданием ищите запись через `list` + `filters` — идемпотентности нет.
2. Для обновления передавайте только изменяемые поля + `id`; для создания — обязательные
   поля и «технические» (`options`, `wageOptions`, `deposit`, `bonus`, `status`,
   `payBox`, `shift`, `pays`, `number`).
3. Фильтруйте через `filters`; `columns` используйте только для строковых `equal` и
   числовых `> < >= <=`.
4. Удаляйте по одному `id` для депозита; для остальных — массивом.
5. После удаления проверяйте, что запись исчезла из `list` (в `load` она останется).
6. Обрабатывайте `200` + `success: false` как ошибку и показывайте `message` пользователю.
7. Соблюдайте ~10 запросов/с; на демо ответы занимают 200–500 мс.
